## Admission, deadlines and ownership transitions

`P:wasm/issue65_control.cc` is the authority throughout this section. Constructor line48 starts the separate handshake budget with command0. Auth completion calls finish (95): FLUSHING waits until all produced bytes are ACKed, then enters IDLE and disarms the handshake clock (82–89). The first command is not covered by an inherited handshake deadline.

Each outer loop iteration emits ARM_COMMAND (`P:probe:100`). Controller line97 checks the gate and sets `armed=true`; it does not admit. The first readCb with available input clears armed, optionally observes the HOLD seam, unlocks I/O and calls admit at81. Under the same gate as capture, admit validates the live session and fence, requires IDLE, changes to RECEIVING, increments command identity and arms the exact nanosecond budget **before popping any current-command byte**. Subsequent partial-header/body reads keep that token and start time. With no queued bytes it waits without spending command time. An EOF with no bytes is retirement, not a newly admitted command.

EXECUTE_START at98 checks fence/poison/closing and unexpected EOF and changes phase/executions; it intentionally neither increments identity nor restarts the deadline. No missing NET-buffer fallback is needed for the selected path. After dispatch, the loop flushes native output, invokes COMMAND_COMPLETE and waits for delivery ACK before IDLE/disarm and the next ARM_COMMAND. No-response LONG_DATA and STMT_CLOSE still traverse the same read/admit/dispatch/finish loop; their produced offset may be unchanged, so the ACK predicate can finish immediately. QUIT takes CONNECTION_COMPLETE/retirement. They do not merge command identities because no SQL response was produced.

| Next-command queue position | Consequence in this exact source |
| --- | --- |
| Zero bytes | readCb waits; prior command is finished, clock disarmed, next token unchanged until data exists. |
| Partial header or partial body | First available header byte admits one fresh token; incomplete input stays RECEIVING and spends that command's deadline; later reads do not rearm it. |
| Complete command, including multiple commands in one DATA | Current packet consumes exactly its own bytes. Next packet stays in the guest deque until prior finish/ACK and next readCb; it receives its own admission/token/deadline. |
| Next bytes queued while prior output is blocked | Prior phase remains EXECUTING or FLUSHING and its clock remains armed; capture is busy. Next command has not been admitted and cannot execute early. Queued residence is not a second concurrent SQL deadline. |
| EOF with queued/incomplete bytes | readCb consumes queued bytes first; after exhaustion EOF returns0. EXECUTE_START rejects non-QUIT when inputEOF is already set; incomplete admitted commands go through fatal retirement handling. This is not permission to execute a pipeline after peer loss. |

The contract is **first byte admitted for the current command**, not host socket receipt of a future queued command. Gate81 and tryCapture136 serialize admission/capture. Raw pending deque bytes may coexist with IDLE; a successful fence then prevents their admission before any pop, while an admitted partial/full command makes capture busy. A delayed STATE/CREDIT observation confers no capture authority. State frames can coalesce, so they must not be used to prove every intermediate event occurred.

EXPIRE at166 first matches epoch/slot/generation (73), then rejects a different command or IDLE/RETIRING. Between old completion and new admission, phase is IDLE, so the old token is stale; after admission the increment rejects it again. The local timer at77 and finish/admit all hold gate; it evaluates the current Budget rather than a stored old timer callback. These facts exclude the suspected stale-token crossover through NET read-ahead, not arbitrary counter exhaustion or a general asynchronous watchdog theorem.
