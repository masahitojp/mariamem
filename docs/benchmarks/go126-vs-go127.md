# Go 1.26.8 vs 1.27.2 — mariamem execution performance

## Scope and provenance

This investigation is independent of the approved v0.4.6 Human Review.
It does not change the generated code, converter, guest, mmap, Snapshot implementation,
public API, module minimum or driver. Main merge and release remain separate.

This report and its evidence were subsequently collected on main as historical
measurement knowledge. The tested source remains the SHA below; importing these
documents does not qualify a newer main SHA or integrate the measured branch's
implementation/benchmark changes.

Both binaries use source commit `80a37385f9d1eda6604358dd5ba2235feb0b26ca`:
accepted candidate `2432abd5439d8daa2ead9676c8c2561ad807b280` plus opt-in benchmark
observations/serial orchestration and approval documentation. Production source is identical.
Generated/guest/backing/Snapshot tree identities are recorded separately in environment.json.
Actual compilers are Go1.26.8 and Go1.27.2 darwin/arm64 with `GOTOOLCHAIN=local`.
macOS Darwin27, arm64, 8 CPU, 16 GiB RAM; one campaign at a time.

Build flags are identical: `-p 1 -trimpath -buildvcs=false`.
The preflight VCS auto annotation differed between toolchains in a Git worktree;
no timing from those preflight binaries is used. Both final builds disable that
annotation and bind source through verified Git commit/tree and binary hashes.
This is source identity handling, not a runtime/compiler correctness workaround.
SDK1.27.2 checksum is checked against the [official download manifest](https://go.dev/dl/?mode=json&include=all).
Task-local module/compiler caches and initial build costs are outside timed suites.
Compiled binaries run directly, never through toolchain auto-switching.

## Methodology

Reuse benchmarks/ownedprepared fixture and application-connection SQL assertions.
Four disposable DB tests per suite; light, 10 MiB/eight-table serial and four-parallel,
and 100 MiB/eight-table serial. Each ordinary cell has 30 fresh-process trials per
compiler/mode; heavy 100 MiB has six. One excluded four-DB warm-up suite per cell.
Adjacent trials alternate AB and BA (ABBA), as does Fresh/Fork order.
A separate 30-trial light persisted round-trip records LoadSnapshot timing.

Same `GOMAXPROCS=8`, `GOGC=100`, `GOMEMLIMIT=off`, empty GODEBUG and GOEXPERIMENT;
same source, fixture, options, guest and environment. Prepare and Snapshot are
charged once to Fork, setup once per Fresh child. Timings keep startup, SQL, Close
and preparation separate. Point SELECT includes first client connection; warm COUNT
is a separate query. INSERT/UPDATE/commit/rollback have nested diagnostic timers;
those timers are not added again to suite cost.

Suite wall excludes external OS-counter observations/final diagnostic GC; process CPU
includes benchmark/diagnostic work as in the existing harness. MemStats is sampled
before/after workload, before final forced diagnostic GC. This GC is benchmark-only,
not a production change. Mallocs/TotalAlloc are process-suite deltas, not database-only
allocations or testing.B allocs/op. Divide by four only as amortized allocations/test,
including preparation. RUSAGE peak RSS includes Go, mmap and other process pages;
HeapAlloc/HeapSys describe Go heap only. RSS is not physical footprint and neither
is virtual address reservation. Existing OS helper retains separate footprint samples.

Disk guard: budget12 GiB, minimum free12 GiB, 240s cell timeout. Maximum four active
DBs; runner stops on observed completed-cell peak RSS over6 GiB. This is not an
in-process continuous hard memory cap. Full raw JSON and observed guard peaks retained.

p50/p95/min/max use all samples; no tail removal. Suite comparisons use 30 independent
process trials (six heavy), not 120 children as independent trials. Startup/SQL pooled
sample percentiles are descriptive. Paired bootstrap uses each process-trial median,
2,000 resamples with fixed seed; confidence intervals are exploratory, not corrected
for multiple comparisons. A narrow interval alone is not evidence of practical value.

## Possible explanations to test

[Go1.27 official release notes](https://go.dev/doc/go1.27) describe size-specialized
small allocations and an experimental opt-out, closure-code sharing, and JSONv2 backing
for encoding/json. Allocation-heavy code and prepared-manifest parsing may be affected.
They do not establish a mariamem performance gain, GC gain or scheduler improvement.
The generated WASM memory-access code is unchanged; compiler effects must be measured.
Profiles can identify changed execution shares but do not alone prove a causal compiler
optimization. Controlled GOEXPERIMENT rebuilding is optional further attribution,
not grounds for changing the product implementation in this task.

## Profile interpretation

Separate diagnostic runs use 20 DBs with the same 10 MiB fixture; never pooled
into timing trials. One CPU and sampled alloc_space profile per compiler/mode.
Single profiles are descriptive, not statistically replicated causal experiments.

Fresh CPU: MemoryInBounds flat share14.34%/11.91%, MemoryEA flat7.82%/6.32%,
pthread_cond_signal21.22%/24.54% (1.26/1.27). Fork pthread_cond_signal/wait
shares29.74%/15.38% versus28.72%/15.48%. These are sampled shares of different
totals, not an isolated bounds-check or scheduler benchmark. CPU profiles include
startup/setup/queries/Close together. The profiles do not justify removing checks,
changing threading or asserting a compiler optimization cause.

Fresh sampled allocation bytes are5.77/5.80 GiB across20 DBs. About80% in both
is `internal/generatedgo/code/base.resizeMemData`: memfs byte-buffer growth,
**not the mmap linear-memory backing**. Driver/wire/framing buffers follow.
The mmap remains outside Go heap. Large filesystem buffers dominate allocation
bytes, so an official small-object optimization need not change suite cost.
This is an explanation consistent with the profiles, not proof of causality.

Potential later investigations: attribute filesystem buffer growth allocations or
generic memory-check/thread synchronization cost with separate correctness gates;
no buffer/check/thread optimization is implemented or approved by this result.

No substantial performance signal justified an additional GOEXPERIMENT build or
Go1.26.9 matrix. Those would be separate bounded attribution questions if later
real-workload evidence contradicts this result. No performance fix was implemented.

## Limitations

- One macOS arm64 laptop, warm OS cache, no controlled CPU frequency/thermal state.
  ABBA mitigates order bias but does not eliminate OS noise or carry-over.
- Six heavy trials do not establish a stable p95. Startup/SQL pooled percentiles
  contain correlated children; inference uses trial clusters.
- Synthetic setup/CRUD and scan workloads, not all application/ORM patterns.
  No Ubuntu or Python-front-end performance matrix in this investigation.
- Same guard/helper machinery may perturb both versions; small deltas are not
  portable performance promises. Profile sampling adds separate diagnostic overhead.
- HeapAlloc is sampled, not peak heap. No isolated per-SQL allocation attribution.
  CPU includes final benchmark diagnostic GC; GC counters exclude that final GC.
- Build times are explicitly separate; cache prefill was not a controlled cold-build
  competition and is not used to recommend a compiler.

## Recommendation

1. **Go1.27 speed improvement: not demonstrated.** Direction varies; suite paired
   intervals all include zero. No meaningful general regression established either.
2. **Migration: compatible choice, not a performance-motivated requirement.**
   Existing accepted consumer compatibility stands. Keep the current canonical build
   policy; do not switch release compilation solely on these measurements.
3. **Keep Go1.26 support and go.mod1.26.0.** Both compilers execute the fixture and
   transaction assertions successfully. No support blocker was found; driver1.9.3
   and production implementation remain unchanged.
