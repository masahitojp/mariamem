## CoW usability failure explained precisely

Current code maps prepared file descriptors with `PROT_READ|PROT_WRITE` and `MAP_PRIVATE` (`prepared_files.go:47`). That supplies OS page-level CoW of **cold prepared files**, not cloning MariaDB execution state. Current architecture :300-310 and characterization :7-13 already make this distinction accurately.

The confusing path is: README :13-14 / guide :7-8 → v0.4.0 integrated report :115 → bare “No CoW ... is introduced”. That sentence describes what **a particular pre-sizing change** did, whereas a newcomer seeks what **the current product** does. Architecture first requires reading 299 lines of migration/build/release material before reaching its clearest current CoW explanation. The correct diagnosis is documentation layer/scope placement; simply removing historical evidence would destroy useful knowledge.

User contract can say only: a Snapshot is cold initial database state; each child starts independent mutable MariaDB; no live runtime is cloned; no memory-sharing or zero-incremental-memory guarantee. Detailed MAP_PRIVATE behavior belongs in current architecture, with explicit separation from runtime-state/image CoW proposals. This wording is a cleanup candidate, not an audit-approved contract.

## Documented intent vs maintainer intent

`docs/python.md:97` deliberately documents shared class mutations, and `:60-62` deliberately documents explicit retained/reopenable destinations. Those are accurate current implementation descriptions. They do **not** establish demonstrated product use cases: the maintainer clarified during this audit that there is no intentional dependence on path writes/Destination, Snapshot.open or class/session mutable sharing, and those APIs were adopted when the concept was introduced. “Documented” and “needed by the current user” must remain separate inventory fields. The separate choice to retain an explicit import boundary is still a current audit input, not evidence of historical use.

## Enduring decision candidates (not all experiments become ADRs)

1. Whole-database disposal is the isolation boundary; setup reuse does not imply shared mutations. This audit must decide the exact product contract before turning current implementation into a requirement.
2. Cold prepared-file reuse + fresh MariaDB execution; no live heap/thread/TLS/waiter restoration (architecture :67-70 / reentry report). Useful current constraint, preserve short rationale + links to rejected reentry evidence.
3. Single supported generated-Go runtime; retired Wasmer paths remain historical tags/reports, not live fallback (current retirement).
4. Cooperative lifecycle vs hard failure containment and full-guest race limitations (still applicable, not “harmless”).
5. If approved separately, validated exact owned backing and explicit import boundary; current spike evidence does not make this selected production policy.

A small `docs/decisions/` could own these continuing constraints with status/scope/rationale/source links. Do not migrate all ~45 reports to ADR format. No current dedicated decisions directory exists.
