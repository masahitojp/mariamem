# Snapshot／MemFS投資判断の再評価

2026-10-14。既存証拠の照合のみ。新規計測・実装なし。**Human decision pending**。

## Human Review

今決めることは、直接コピーを製品化するか、その前に限定追加確認へ投資するか、現行維持で区切るか。
**推薦は、直接コピーに限った追加確認への投資（上限4エンジニア時間）**。
10 MiB・4 Forkでは準備から後片付けまで約0.225秒／11.4%短縮しており、
利用者の利益をSnapshot単体だけの成果として扱うべきではない。一方、100 MiB・16 Forkの
全体時間は改善・悪化が混在し、候補に起因する持続的な悪化かは未確定。
製品化へ見込む12～24エンジニア時間の前に、その判断材料へ小さく投資する順序を勧める。
時間は後述の作業分解に基づく担当者の概算で、実測工数や完了保証ではない。

最も強い反論は、既に追加8試行を行い結論が混在したのに、また調査へ費用を使う点である。
単に同じ測定の回数を増やすことは推薦しない。既存データにない子区間のGC処理費用・待機・
割当寿命の関係を、採否に必要な範囲だけ判別する価値があると評価した。
ただし4時間で判断できなければ「追加確認完了」とせず、未判定を明示して現行維持を推薦し、
自動継続しない。この限定的な再開には新しいHuman承認が必要である。

以前の「現行維持」推薦は、大規模ケースの不確実性を重く置き、実測された小～中規模の
全体利益と製品化費用を同じ表で比較していなかった。今回の推薦変更は、その比較の修正である。
既存の停止判断を撤回済みとは扱わず、承認までは停止を維持する。

## 1. 共通の評価基準

三案を次の同じ基準で比較する。全ケースで必ず高速化することも、一般的な性能安全性の証明も要求しない。

1. 利用者の利益：準備、Snapshot、全子のSQL、Closeを含む時間。Snapshot応答時間と物理メモリも別に評価する。
2. 証拠の強さ：観測結果、原因の説明、未測定範囲を区別する。二試行の中央値を安定した改善率にしない。
3. 不利益：遅くなる可能性のある用途、保持容量、子間隔離・破損検出・失敗時の扱い。
4. 投資：残る実装、対応言語・OSの検証、継続保守、判断を得る費用。

旧[Architecture Decision](memfs-architecture-decision.md)の10%時間/CPU、または20%かつ32 MiBの
物理メモリ改善は投資の目安。全用途一律の性能保証ではない。今回、直接コピーの中規模ケースは
時間の目安に達する観測がある。累積allocation削減を物理メモリ削減へ読み替えない。

## 2. 既存のFresh／Snapshot測定をどう使うか

[v0.4.5 crossover](../../benchmarks/v045-measurement.md#actual-suite-crossover)では、軽い準備の
4 DBはFresh 0.291秒／Snapshot-Fork 0.656秒、10 MiB・4 DBは2.540／1.397秒、
100 MiB・4 DBは23.971／7.821秒。既に「軽い準備はFresh、重い準備は再利用」という判断材料がある。
[v0.5.0測定](../../benchmarks/v050-product-verification.md#user-visible-suite-time)でも、Goの
10 MiB・4テスト直列はFresh 2.870秒／Fork 1.681秒（各3試行中央値）。100 MiBは25.447／9.994秒
だが各1試行。前者の傾向を再確認するためだけに新しいdogfoodを先行させる必要はない。

これらは異なるguest・source・schema・startup-tail状態の歴史的証拠。
現在のmainの速度保証でも、直接コピー候補との対照測定でもない。
[v0.4.6製品比較](../../benchmarks/v046-product-validation.md)は軽い準備や並列時の例外も残す。
軽いSnapshotケースの改善率を、Freshより有利になったという主張へ使わない。

## 3. 直接コピーの利益と、大規模の不確実性

既存[spike][spike]はGoの一時Snapshotのみ。guestのコピー、元DB消費、最終保持ファイルの検証、
ForkのMAP_PRIVATEは維持する。Python・永続Snapshot・LoadSnapshotの高速化は実装していない。

| ケース（全体時間） | 元 → 直接コピー | 観測された利益と限界 |
| --- | ---: | --- |
| 最小・4 Fork | 0.791 → 0.591秒 | 約0.200秒／25.2%。ただしこの用途自体はFreshが有利な可能性があり、Fresh対照ではない |
| 10 MiB・4 Fork | 1.979 → 1.754秒 | 約0.225秒／11.4%。準備再利用が役立つ中規模用途にも全体利益がある |
| 10 MiB・16 Fork | 4.365 → 4.088秒 | 約0.277秒／6.3%。Snapshot一回の節約はFork数に比例しない |
| 10 MiB・16 Fork・4並列 | 3.316 → 3.175秒 | 約0.141秒／4.2%。並列でも利益の観測はあるが範囲は重なる |
| 100 MiB・4 Fork | 12.192 → 11.762秒 | 約0.430秒／3.5% |
| 100 MiB・16 Fork、初回通常測定 | 26.315 → 25.887秒 | 約0.428秒／1.6%。別の資源観測一組では4.5%悪化 |
| 同条件、追加通常測定 | 25.128 → 25.671秒 | 約0.543秒／2.2%悪化 |
| 同条件、追加資源観測 | 26.204 → 25.457秒 | 約0.747秒／2.9%改善 |

通常測定は各モード2試行、追加資源観測も各2試行。異なる観測条件を混ぜて平均化しない。
Snapshot単体は追加確認でも約0.43秒短縮、累積allocationは約264 MiB減った。
追加資源観測のPeak RSSは元1077～1177 MiB／候補1045～1076 MiBだが、安定した削減率の証拠には足りない。

### 悪化について分かること／分からないこと

- **確認済み：** 資源サンプリングなしでも候補の全体が遅い比較がある。「計測器だけのせい」とは言えない。
- **確認済み：** 追加通常測定では準備が中央値で約0.313秒、子区間が約0.655秒長い。
  直接コピーを実行する前の準備にも差があるため、全差をコピー方式の効果とは扱えない。
  起動時の環境分岐等まで厳密に同一という意味ではない。
- **確認済み：** 通常測定の範囲は元24.245～26.011秒、候補25.322～26.020秒で重なる。
  先の一組は候補が1.077秒遅く、順序を反転した一組は差0.009秒。資源観測の二組は候補が速い。
  重なりは同等性の証明ではなく、持続的な回帰の大きさを決められない理由である。
- **確認済み：** 資源観測の子区間でGC回数は元0/0、候補18/16。候補の方が速い組にも現れる。
- **今回の既存データ再集計：** 同区間の`PauseTotalNs`差は元0/0 ms、候補2.327337/1.911831 ms。
  これは停止時間の集計であり、並行GCや割当時のGC作業、スケジューリング影響を含む総費用ではない。
  「GC停止だけで秒単位の悪化を説明する」という解釈は支持されない。
- **未解決：** 割当寿命の変化が子のCPUや待機へどれだけ効いたか、通常の実行ばらつきと候補由来の影響の内訳。
  候補に起因する遅延の再現性・頻度も確定していない。

従って「候補が大規模用途を遅くすることが確定」も「全部ばらつきなので無視できる」も採らない。
機能上は既存SQL・所有権・破損検出・失敗cleanup検証が通っており、性能の未判定をデータ破損へ拡大しない。

再集計元は[追加確認の保存データ][raw]の`resources-{0-original,1-direct,2-direct,3-original}.json`。
各ファイルの`resources.children_closed_go`から`resources.snapshot_go`の`num_gc`と`pause_total_ns`を引いた。
計測器の対応は`benchmarks/ownedprepared/resources.go`（`runtime.MemStats.PauseTotalNs`）。新規実行なし。

## 4. VFS／MemFS／pgmem比較の更新

| 従来の候補 | 今回の証拠で更新される評価 | 利益と費用の判断 |
| --- | --- | --- |
| 現行維持 | 再利用の既存利益は成立。追加のSnapshot待ち約0.2～0.43秒は残る | 最小費用。ただし短縮可能な待ちを残す機会費用がある |
| 小幅改善：直接コピー | 仮説から、所有権を保った実装可能性と小～中規模の全体利益の観測へ進んだ | 現在もっとも具体的な改善候補。大規模の性能判断と製品化は残る |
| 小幅改善：MemFS成長倍率 | [限定計測][memfs]で再確保は判明。実要求モデルで累積確保−20 MiB、コピー−23 MiB、最終余り＋3.7 MiB | 直接resize時間は約917 ms中11.6 msの一試行。直接コピーより利用者利益の根拠が弱い。間接GC費用まで1.3%に制限したわけではない |
| 保存方式：sparse/chunk | 約143 MiBの未書込予約を確認したが、削減可能RAMは未確定。Snapshotでは全論理bytesをコピーする | 未使用範囲の発見だけでは、広いI/O・予約・zero/truncate・export変更の費用を正当化できない |
| 保存方式：mapped prefix＋tail | 今回の6子で成長による全file detachはゼロ | 該当パターンの利益が観測されておらず、直接コピーに優先させる理由はない |
| pgmem型heap Clone／file単位CoW | Snapshotのmaterialization回避は有望な原理。今回、既存方式のままでも約半分に短縮できた | 全体の不安定さはfile方式の限界を証明しない。より広い置換を必要とする根拠は増えていない |
| Overlay／外部block VFS全面導入 | 今回の結果は新しいnamespace合成や永続block storeの要求を示さない | 既存の置換非推薦を変える利益の証拠なし |

[pgmem調査](pgmem-vfs-design-review.md)の固定ソースでは、Clone時はmetadataを独立化しbytesを共有、
最初の小さな更新でも対象file全体をheapへコピーする。現行mariamemのMAP_PRIVATEはOSページ単位で
独立化する。pgmemは大きな初回予約も連続bufferであり、sparseの既成解ではない。
heap Cloneへ移るなら永続保存・Pythonのprocess間受け渡し・GC寿命・全write入口の所有権が変更対象になる。
pgmemの約10 msという別条件の値を、その利益や目標値には使わない。

[pglite調査](memfs-optimization-discovery.md)のwritable-open時copy-up、
[block storage調査](block-storage-design-discovery.md)の外部store/cache/restoreの費用も残る。
直接コピーの全体結果が混在したことから、これらの方式なら改善すると推論はできない。
旧資料のFd_allocate縮小欠陥はv0.5で修正済みであり、今回の未解決項目へ戻さない。

## 5. 製品化の残作業と費用

試作実装は固定main `2550bbe1ccf58f9cf65cf4cd801224907a7f9469`から測定source
`3341f99000246fc64ae17b4ea39118f55589de1e`への6ファイル、339行追加／4行削除。
うち新規失敗テストが160行。差分量は工数の証明ではないが、全面VFS置換と同じ費用には扱わない。
コード照合対象は`SnapshotOwned`、`exportInstance`、`MaterializeDirect`、公開`Snapshot`の分岐。

最小の採用対象は**Goの一時Snapshot**。この対象の利益と費用を三案とも共通にする。
Python同時高速化・永続形式変更を勝手に追加して採用費用を膨らませない。

| 作業 | 内容 | 担当者の概算実働 |
| --- | --- | ---: |
| 試作の製品化 | markerファイル／環境変数／任意interface分岐を明示的な内部受け渡しへ整理。受理前後のエラーと既存経路を維持 | 4～8時間 |
| 正確性・寿命の確認 | 保持FDの再検証、破損・短いcopy・途中失敗、元DB消費、親Closeと生存子、子由来Snapshot、並行利用を既存oracleで確認 | 4～8時間 |
| 統合と対応OS確認 | macOS／Ubuntuの対象境界、製品化後の同条件時間確認、既存Python経路の回帰、source/文書整合 | 4～8時間 |
| **合計** | Go一時Snapshotのみ。新たな性能修正が必要ない前提 | **12～24時間（8時間日換算1.5～3人日）** |

これは見積もりで、既存作業の計時ではない。CIの待ち・新たな性能修正・最終Release Qualificationは含めない。
試作時に残ったpublication-boundaryの既存`.log`違反は、統合時に現状を確認し、残存すれば別途解決が必要。
未解決のままguardを通ったと報告しない。Python高速化を選ぶ場合はprocess間の所有権・受け渡し設計の
別見積もりが必要で、上記費用にも効果にも含めていない。

## 6. 三案を同じ基準で比較した結論

| 選択 | 得られる／見送る利用者利益 | 残る不利益・不確実性 | 追加投資 |
| --- | --- | --- | --- |
| **直接コピーの採用を決めて製品化** | 観測されたSnapshot約0.2～0.43秒、小～中規模の全体約0.2～0.35秒の短縮を届ける候補 | 大規模で持続的に悪化するかは未確定。現時点で安定した全体改善を約束できない。正常系・失敗系の試作証拠はある | 12～24時間＋CI待ち。性能修正が必要なら追加見積もり |
| **限定追加確認** | 上記の利益を採用できるかを、製品化前に判断する材料を得る | 利益を届けるのは遅れる。追加確認しても原因・採否が決まらない可能性 | **上限4時間**。後に採用なら製品化12～24時間が別途必要 |
| **現行維持** | 現在のFresh／準備再利用の利益をそのまま提供。追加保守と実装費用を負わない | Snapshotの短縮可能な待ちと累積allocationを残す。候補が悪いという認定ではない | 新規実験・製品化費用なし。証拠保管のみ |

広い保存方式変更は、直接コピーより追加利益が実証されておらず、変更面は全I/O・所有権・保存・
言語間受け渡しまで広がるため、三案に優先する投資として推薦しない。

**選択は限定追加確認。** 小～中規模の全体利益が既にあり、単なるallocation表示の改善ではない。
一方、大規模の未確定を受け入れて12～24時間を先に投入するより、上限4時間で判断材料を足す価値があると考える。
これが現行維持に勝る理由は、具体的な利用者利益があり、確認費用を製品化費用より小さく固定できる点。
今すぐ採用に勝る理由は、子区間の不利益が明確になった場合の修正費用を、採用前に見極められる点である。

追加確認を選ぶ場合の問いは一つ：**大規模の子区間に、Snapshotの節約を継続的に相殺する
候補由来の費用があると判断できるか**。不足するのはGC回数ではなく処理費用・待機・寿命の帰属。
単なる試行数追加や複数GC設定の探索、VFS改修、新しいdogfoodは含めない。
詳細な実行計画は承認後にこの境界内で作る。ここでは新しい実験を開始しない。

- 費用を具体化でき、利益を打ち消す持続的な悪化を示さない材料が得られれば、残る限定性を示して製品化を推薦する。
  悪化が絶対にない証明を条件にはしない。
- 相殺する費用が確認され、修正が必要なら、修正箇所と費用を提示して停止。修正を追加確認へ混ぜない。
- 上限到達または証拠が混在したままなら未判定を報告し、現行維持を推薦。上限到達を調査完了と呼ばない。

小～中規模のSnapshot応答改善を優先し、大規模の数%程度の観測差を未確定のまま受け入れて製品化を
選ぶことも、合理的な代案として残す。ただし数%は今回の観測幅であり、悪化の上限保証ではない。
この投資判断は最適化の採否であり、リリース承認ではない。

## 証拠・今回の確認

新規実行なし。既存資料と試作差分、保存済みJSONの停止時間差を照合した。
過去資料を上書きせず、推薦変更の理由を本資料へ記録する。現在の承認済み方向は変更していない。
現在のmainは既存のSnapshot停止記録1 commitだけoriginより先行していた。本作業はこの文書のみを追加。
