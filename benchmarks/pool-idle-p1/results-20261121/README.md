# スレッドプールの保守間隔を短くする効果と常駐時のコスト

**一律 50 ms の既定化は見送り、稼働中 50 ms・低頻度時 4 秒を別々に指定する Go 側の試作を推奨する。** 50 ms は P1 のスイート経過を対応中央値で 23.0% 短縮し、前回の P8 でもワーカー補充待ちを縮めた。一方、アイドルの 8 DB では 70–120 秒の CPU が毎秒 2.70 ms から 4.69 ms に、プロセスに計上された割り込み起床が毎秒 59.9 回から 124.7 回になった。CPU の増分は 1 コアの約 0.20% であり、短命なテストプロセスで遅延を優先する用途には 50 ms を支持する材料がある。

分離案では、低頻度モードで 4 秒に延ばした後、最初の SQL がワーカー補充を待つ可能性が判断を左右する。次の試作で比べる対象は現行 400 ms・一律 50 ms・分離案の 3 条件。P8 の遅い投入と P1 の経過短縮を保てるか、8 DB 常駐時の起床が現行水準へ戻るか、低頻度から復帰する最初の SQL に長い待ちが出るかで判定する。今回測ったのは 1 台の Mac の各 2 試行・120 秒で、分離案の測定と製品への採用は今後の判断になる。

### 切断から 70–120 秒

| 保持DB数 | 設定 | CPU ms/秒 | 割り込み起床/秒 | パッケージアイドル起床/秒 | 保守呼び出し/秒 |
|---:|---:|---:|---:|---:|---:|
| 1 | 400 ms | 0.52 | 10.03 | 0.04 | 0.24 |
| 1 | 50 ms | 0.74 | 15.70 | 0.08 | 2.00 |
| 8 | 400 ms | 2.70 | 59.92 | 0.48 | 1.92 |
| 8 | 50 ms | 4.69 | 124.69 | 0.99 | 20.65 |

| 保持DB数 | 設定 | CPU ms/秒 | 割り込み起床/秒 | パッケージアイドル起床/秒 | 保守呼び出し/秒 |
|---:|---:|---:|---:|---:|---:|
| 1 | 400 ms | 0.94 | 19.10 | 0.15 | 2.47 |

各列はプロセス全体の 2 試行平均。CPU は user+system の実行時間で、10 ms/秒は 1 コアの 1% にあたる。割り込み起床とパッケージアイドル起床は macOS がこのプロセスに計上した回数。消費電力は測定していない。2 試行の生値と区間幅は別表に保存した。[各試行・区間](idle-windows.csv) · [70–120 秒の平均と範囲](idle-steady.csv)

固定ソースは、待機ワーカーがいてアイドルと判断した状態が 1 分を超え、アクティブなワーカーが空のときに低頻度モードへ切り替える。低頻度モードでは通常間隔の 10 倍を設定する。したがって今回の実験設定は、低頻度モードも 4 秒から 0.5 秒に変える。[移行条件](https://github.com/MariaDB/server/blob/e4549ea60c98a8743ed4743d7f92174d8a0005d9/tpool/tpool_generic.cc#L550-L583) · [間隔の設定](https://github.com/MariaDB/server/blob/e4549ea60c98a8743ed4743d7f92174d8a0005d9/tpool/tpool_generic.cc#L874-L895)

8 DB では切断後 30–70 秒に全試行で低頻度への切替を 8 回ずつ観測した。後半の保守呼び出しは 400 ms の 2 試行がともに毎秒 1.92 回。50 ms は順に 15.88 回、25.42 回だった。2 試行目では SQL を発行していない後半にも通常モードへの切替と新規ワーカー開始を各 1 回観測した。CPU と起床の範囲にはこの実際の動作も含めた。プールを合算したカウンターでは 1 件の切替を起こしたタスクまでは特定できない。[モード切替・実効間隔](idle-phases.csv)

## P1 で短くなった時間

| pgmem 由来のモデルケース | 400 ms | 50 ms |
|---|---:|---:|
| スイート数 / サンプル投入数 | 48 / 1,008 | 48 / 1,008 |
| スイート経過の中央値 | 1,628.9 ms | 1,247.7 ms |
| プロセス CPU の中央値 | 1,233.0 ms | 1,200.8 ms |
| 21 回の投入に費やした合計時間の中央値 | 729.2 ms | 733.1 ms |
| 投入以外の経過時間の中央値 | 901.1 ms | 514.8 ms |
| 全投入の最大 / 400 ms 以上の件数 | 50.1 ms / 0 件 | 50.6 ms / 0 件 |

1 組の中の相対差を 48 組で集計すると、スイート経過は中央値 −22.96%（二項順位の 95% 区間 −23.68〜−22.47%）、CPU は −2.15%（−2.85〜−0.88%）。P1 では 21 回の投入区間は直列で、短縮は主にその前後に現れた。最後の 400 ms 設定のスイートで保存できた全区間を見ると、セットアップの import が 477.8 ms。全 48 組について短縮分を import に帰属させるには、両条件の区間別記録が必要になる。[設定別集計](p1.csv) · [投入内外](p1-sample-time.csv) · [対応差](p1-delta.json) · [最終スイートの区間](p1-main-48-1-400-trace.json)

前回の P8 は各設定 96 スイート・2,016 投入。400 ms 以上の投入が 7 件から 0 件、最長 475.4 ms から 153.9 ms、ワーカー補充を待ったキュー時間が 382–395 ms から 27–50 ms になった。P8 は並列投入時のまれな待ち、P1 は主に投入以外の経過時間に効果が現れた。[P8 の比較と経路照合](https://github.com/masahitojp/mariamem/blob/2dedb9f95fd373d612166538187e47cdc5f860c4/benchmarks/p8-maintenance-period/results-20261121/README.md)

## 条件と検算

リング候補 a1ce4a7d、二重書き込み既定 ON、Apple M1。各条件で同じバイナリに同じ SQL を与え、Go ビルドのオーバーレイで保守間隔の初期値だけを選択した。P1 は GOMAXPROCS=1、test.parallel=1、各スイートは読取 50・更新 20・投入 21。アイドル測定は GOMAXPROCS=8、同じプロセスに fork を 1 個または 8 個保持。全接続を閉じてから 120 秒間 SQL を発行せず、保持前後に全 DB の 40 注文・100 明細、注文合計と明細合計の両方が 1,888,173 セントで一致することを検査した。全 8 試行で一致した。[事前条件](protocol.md) · [元の観測値](runs) · [再現手順](recipe/REPRODUCE.md)
