# P8の約390 msをタスク登録からワーカー起動まで追跡

**遅延を減らす次の候補は、模擬I/Oのワーカーを補充する保守タイマーの間隔。** 400 ms以上かかった11投入のすべてで、対象タスク登録時にプールは追加ワーカーの生成を試みたが、生成中フラグが立っており引き返した。2つのpurge処理が待機してキュー取り出しが止まり、保守処理が新しいワーカーを起動すると処理が再開した。フラグを観測したのは登録時であり、その後の全期間でフラグが立ち続けたかは不明。[11件のワーカー時刻](worker.csv) · [生イベントとの照合](verification.txt)

| 11件に共通する区間 | 各区間の最小–最大 |
|---|---:|
| 登録 → プールの最初の判断 | 0.00013–0.01688 ms |
| 登録 → 保守処理が新ワーカーの生成を呼ぶ | 374.75–398.07 ms |
| 生成呼び出し → 同じワーカーのworker_main開始 | 0.038–0.232 ms |
| worker_main開始 → プールの最初のタスク取得 | 0.002–0.012 ms |
| プールの取得再開 → 対象タスクの取得 | 0.12–2.11 ms |
| 対象タスク取得 → 対象コールバック実行 | 0.00008–1.42 ms |

待機中の既存ワーカーへnotify_oneを送る分岐を取ったケースは、対象の初回判断11件では0件。登録時はプール内に待機リストから起こせるスレッドがなく、生成試行に進んだ。回復時は保守処理による生成呼び出し、同一worker_dataのworker_main開始、同じワーカーの最初のキュー取得を確認した。以降は複数のワーカーが先行タスクも処理する。task_group経由ではキューから取り出したスレッドと実コールバックを実行したスレッドが異なるため、両段を別々に照合した。[時刻とワーカーID](worker-details.json)

プール全体で取り出しが途絶えた最長区間は374.83–398.22 ms。その全例で同じプールの別々のワーカーが purge_truncation_callback と purge_coordinator_callback の処理中にfutex待ちに入り、両方の待ちがその区間の99%以上と重なった。MariaDBの固定ソースでは保守タイマーの初期間隔は400 ms、生成中の多重生成を防ぐ判定がadd_threadにある。観測した復帰は保守コールバックの動的実行中だった。待っていたSQLは書き込み完了通知で再開した。[生成判断とタイマーの固定ソース](https://github.com/MariaDB/server/blob/e4549ea60c98a8743ed4743d7f92174d8a0005d9/tpool/tpool_generic.cc#L666-L805) · [ゲストの照合情報](upstream.json)

## どのI/Oが待ったか

| doublewriteの実効値 | 400 ms以上の投入 / 2,016 | ページの最初の模擬I/O | 先行する二重書き込みバッチの模擬I/O | ページの完了タスク |
|---|---:|---:|---:|---:|
| ON（既定） | 4 | 1 | 3 | 0 |
| OFF（Forkの投入直前に変更） | 7 | 2 | 4 | 1 |

先行バッチ7件は、そのページのデータファイルI/Oを実際に発行したコールバックから親のI/Oタスクまで引き戻して照合した。残る1件（OFF、ブロック58）はページの最初のI/Oタスクが0.90 msで実行された後、完了タスクが385.52 ms待った。この例もプールの生成判断・purgeの待ち・保守処理による再開は同じだった。全DBのキューで100 ms以上待った初回模擬I/Oは583タスクあり、同時に滞留した他のタスクも含む。投入11件の内訳には同じページ・要求に対応したタスクだけを使った。[スイート集計](summary.csv) · [投入ごとの値](samples.csv) · [前回の設定比較](https://github.com/masahitojp/mariamem/blob/b878cfbd7b7c7f7b4adba952b420ba70b5b8965f/benchmarks/p8-flush-settings/results-20261121/README.md)

## 条件と判断

Apple M1、Go 1.27.4、GOMAXPROCS=8、GOGC=100、固定リング候補a1ce4a7d。pgmem由来の50読取・20更新・21投入、各設定のウォームアップ後に96組をAB/BA交互に実行した。各Forkで設定読戻し、意味テストと全ケース成功を確認した。計測対象が最初の96組で再現したため事前指定の追加96組は不要だった。これはGoビルドオーバーレイによる観測で、各方式の発生率・対策の効果・製品採用を判定する試験ではない。既定設定は維持し、次の検証はこのプールの保守間隔だけを変えた実験用オーバーレイで、遅い投入・通常のCPU・ワーカー生成数を比較することを勧める。[再現・観測器の説明](recipe/REPRODUCE.md)
