今回の記録は各段で時刻と回数を更新しており、タイミングに依存する現象の再現性は変わりうる。次に証拠を取る場合は、前回の軽い計測を基にし、平常時の追加を対象タイマーの退出・再挿入完了の通番とハンドラ識別に絞る。通常モードで 4 秒超を検出した時だけハンドラのスタックと直近の通番を保存する構成を推奨する。例えば最大 12 組なら本計測は約 54 分、ビルドは別途。異常 1 件の取得で終了し、未再現なら原因は保留のままとする。

## タイマーが通る経路

保守タイマーはスレッドプールを示す引数が null の状態で構築される。この場合、mysys のタイマースレッドが期限切れのタイマーをヒープから取り出すと、タイマーの実行関数から保守処理を直接呼ぶ。保守が戻ると周期を再確認し、次の期限でヒープに挿入する。ワーカー用のキューにタスクを送る分岐は、別のタイマー構成で使われる。保守処理自身は、滞留した仕事にワーカーを追加しうる。[保守タイマーの構築](https://github.com/MariaDB/server/blob/e4549ea60c98a8743ed4743d7f92174d8a0005d9/tpool/tpool_generic.cc#L781-L785) · [実行経路の選択](https://github.com/MariaDB/server/blob/e4549ea60c98a8743ed4743d7f92174d8a0005d9/tpool/tpool_generic.cc#L321-L336) · [発火から再登録まで](https://github.com/MariaDB/server/blob/e4549ea60c98a8743ed4743d7f92174d8a0005d9/mysys/thr_timer.c#L258-L294)

固定 guest と対応する関数表を検査し、生成 Go の Fn5495（タイマーハンドラ）、Fn16625（タイマー実行）、Fn16626（保守）、Fn16636（ワーカー用タスク送信）で実測した。DB ごとにスレッド群の識別子、線形メモリ、プール、タイマー本体、ヒープに入ったタイマーアドレスを照合した。対象タイマーから取り出された関数テーブル番号 12334 が Fn16625 を指すことも両コミットで確認した。[関数対応](symbols.txt) · [テーブル照合](table-bindings.json)

## 再生条件と判定範囲

現行 a1ce4a7d（稼働中 400 ms）と分離案 fa7d878d（稼働中 50 ms）、低頻度時は両方 4 秒。Apple M1、macOS、Go 1.27.4。各プロセスで前回と同じ 8 DB に対し、8 秒休止と同時復帰を 8 回、さらに約 70 秒休止と同時復帰を 1 回行う。各波で 4 読取・4 更新、全接続切断、最終在庫と注文内容を検算する。事象判定は各復帰直前の通常モードで最終進入から 4 秒超。計測点以外で一時的に発生して既に解消した空白と、計測追加によるスケジューリングへの影響は残る。段別の回数は各 DB の最終復帰直前までの累積値で、スイート終了後の処理は対象外。[事前条件](protocol.md) · [各波・各DBの観測](snapshots.csv) · [再現手順](recipe/REPRODUCE.md)
