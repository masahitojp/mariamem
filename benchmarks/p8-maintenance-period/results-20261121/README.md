# P8のスレッドプール保守間隔を400 msから50 msにした結果

**50 msを製品化検証に進めることを推奨する。** 詳細診断を外した通常ビルドで、400 ms以上のサンプル投入が7/2,016件から0/2,016件になった。前回と同じ生成見送り→保守処理でワーカー補充の経路をGo側で照合すると、対象キュー待ちは382–395 msから27–50 msに短縮した。通常ビルドでプロセスCPUの対応中央値は−0.10%だった。採用判断に残る主な懸念は、保守呼び出しの増加による常駐・アイドル時のコスト。製品の既定値は今回の実験では変更していない。

| P8の比較（各条件96スイート・2,016投入） | 400 ms以上の投入（400 → 50 ms設定） | 最長投入 | 各スイートの最長投入の95パーセンタイル |
|---|---:|---:|---:|
| 通常ビルド、二重書き込みON | 7 → 0 | 475.4 → 153.9 ms | 444.6 → 116.1 ms |
| 診断あり、ON | 3 → 0 | 465.9 → 126.6 ms | 131.6 → 109.5 ms |
| 診断あり、OFF | 6 → 0 | 475.3 → 137.6 ms | 464.4 → 110.3 ms |

各条件で遅い投入は1スイートにつき最大1件。通常ビルドの96組では400 ms設定だけに遅延が出た組が7、50 ms設定だけの組が0（両側の正確McNemar検定 p=0.015625）。この2,016投入での0件は、今後も一度も生じないという発生率の推定ではない。全体のスイート経過は対応中央値−1.22%（95%区間 −2.32〜+0.33%）。改善の中心は、まれに長引いていた投入である。[対応差](paired.csv) · [スイート別結果](suites.csv)

## 待ちが短くなった区間

前景SQLの待ちと同じページ・タスクに対応し、生成中フラグと保守処理からの新ワーカー起動まで確認できたキュー待ちは、400 ms設定が9件（382.0–395.3 ms）、50 ms設定が12件（26.7–49.9 ms）。50 msでもこの経路は残り、次のワーカー補充までの待ちが短くなった。各設定で観測された別々の事象で、件数は経路を特定できた範囲を示す。前景に対応しないタスクも含めた全DBの初回模擬I/Oキューの最大値は、二重書き込みONで390.6 → 51.5 ms、OFFで403.5 → 52.1 msだった。[経路別集計](mechanism-summary.json) · [タスク別時刻](worker.csv)

## 通常時のコストと判断

通常ビルドのCPUは96組の対応中央値−0.10%（95%区間 −0.69〜+0.33%）。両方の最長投入が400 ms未満だった89組に限ると−0.05%（−0.56〜+0.51%）。診断あり・二重書き込みONの96スイートで起動したワーカー総数は13,411 → 13,674（+2.0%）、1スイートあたりの中央値は138.5 → 140.5。保守コールバックの総数は2,118 → 4,678（2.21倍）。OFFでもワーカー総数は13,261 → 13,548（+2.2%）、保守は2,124 → 4,640（2.18倍）だった。

次の採用判断は、長時間アイドルのDBと複数DB常駐時のCPU・起床回数を対照と比較し、P1など他の並列度でも通常処理への影響を確認した上で行う。今回のデータが支持するのはこのタイマーに限った変更で、リング候補全体の既定化は別判断となる。[親issue #233](https://github.com/masahitojp/mariamem/issues/233)
## 比較条件

Go 1.27.4、Apple M1、macOS arm64、GOMAXPROCS=8、GOGC=100で実行した。固定したリング候補は a1ce4a7d568fbf6eac7bee032a7fdfbe464544fb。pgmem由来のP8モデルケースは1プロセスにつき読取50・更新20・サンプル投入21。診断ビルドは「タイマー2値×二重書き込み2値」の24通りの実行順を4巡した。通常ビルドは二重書き込みを既定ONに固定し、2値の順序を交互に96組比較した。各条件の意味検証と1回のウォームアップは集計から除いた。SQL結果・ケース数・実効間隔を検証できた本計測は計576スイート、12,096投入。[条件別集計](summary.csv) · [全スイート](suites.csv) · [全投入](loads.csv)

Goビルドのオーバーレイで、スレッドプールのコンストラクタFn16634が初期化する保守間隔だけを選択式にした。各モードで同じバイナリを両条件に使い、タイマーを設定する呼び出しの実引数をチェックした。全スイートで22回ずつアームした。MariaDBソース、製品バイナリ、公開APIの変更はない。このフィールドからはプールの低頻度モードの間隔も10倍値として導出されるため、50 msの実験ではそちらも4,000 msから500 msになる。長時間アイドルのDBでのCPUや他プラットフォームは今回の測定範囲外。[実験用変更](recipe/period_overlay.py) · [固定MariaDBのタイマー状態切替](https://github.com/MariaDB/server/blob/e4549ea60c98a8743ed4743d7f92174d8a0005d9/tpool/tpool_generic.cc#L875-L895)

診断のワーカー数は全22 DBで実際にworker_mainに入った回数。キュー時間は同じDB・タスク登録世代・実コールバック引数を照合した。SQLの前景待ちの保存下限は10 ms。DBごとの最大キュー時間は下限を設けず計測する。前回と同じ回復経路と判定したのは、生成中フラグによる追加生成見送りの後、保守コールバックが新ワーカーを生成し、同じworker_dataでキューの取り出しが再開した場合。通常ビルドにはSQL・futex・ワーカーの詳細記録を含めず、時間とCPUはこちらでも独立に比較した。[タスク別の照合](worker.csv) · [検証手順](recipe/REPRODUCE.md) · [前回の経路同定](https://github.com/masahitojp/mariamem/blob/80aee317a1069a629c72d53a8959421f1e4ef70a/benchmarks/p8-aio-worker/results-20261121/README.md)
