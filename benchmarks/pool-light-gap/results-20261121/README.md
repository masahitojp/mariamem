# 軽量監視での保守タイマー再試験（2026-11-21）

現行と分離案を交互に12組、192 DB で比較した。通常モードで保守への進入が4秒以上途絶えたという警報は両条件とも0件。全1,728件の復帰時 SQL と、全192 DB の在庫・注文件数・明細件数・金額の検算が通った。各試行の終了時、192/192 DB で最後の保守進入・退出・次回のタイマー再登録の通番が一致した。

以前、分離案の1 DB では保守の最終進入から126.45秒が経過していても SQL は応答した。今回その事象が起きた時点のスタックは得られず、停止箇所は未特定。固定リング候補では現行設定（通常時400 ms・低頻度時4秒）を維持し、同じ8 DB ベンチでの再試行はここで終了する。 [元の126秒の記録](https://github.com/masahitojp/mariamem/blob/aaabca75ced4876a45f553de940671f3f7e2efc5/benchmarks/pool-reactivation/results-20261121/README.md)

分離案には先行の pgmem 由来モデルケースで利点があった。8並列・各2,016投入では、400 ms 以上の投入が現行5件、分離案0件だった。今回の軽量監視は、当時の性能差とは別に、保守の長時間停止を特定できるかを検査した。 [先行の周期別ベンチ](https://github.com/masahitojp/mariamem/blob/df67fd52e03ea248ff94f4baefe1a3223cc6f273/benchmarks/pool-split-interval/results-20261121/README.md)

## 記録方法

固定リング上の現行 a1ce4a7d（400/4000 ms）と分離案 fa7d878d（50/4000 ms）を、同じ Apple M1・Go 1.27.4 の別プロセスで測った。タイマーの通常動作は前回の軽い計測を使い、保守コールバック Fn16626 の退出と、mysys タイマーハンドラ Fn5495 が同じタイマーをヒープに戻した直後に通番を保存する。再登録の確認にはタイマーのアドレス、ディスパッチ関数、挿入後の例外フラグを用いた。タイマーハンドラの goroutine は開始時に一度識別する。[実行経路の照合](https://github.com/masahitojp/mariamem/blob/2dba44b449d52cf8ca13462b22e3ea0961789250/benchmarks/pool-timer-path/results-20261121/README.md) · [今回の計測箇所](recipe/measure.py)

監視は SQL を実行する goroutine と独立し、対象は計測中の 8 fork。通常モードに入った時点と最後の保守進入のうち新しい方を起点に、4 秒を超えたときだけスタックを取得する。次の検査は最も早く条件が成立しうる時刻に設定する。制御試験では意図的に通番が止まったプールのハンドラをスタック集合から抽出できた。通常モードに戻った直後と低頻度時は検出対象から除外した。[監視コード](recipe/watch.go.txt) · [制御試験の記録](detector-control.log)

各試行は 8 秒切断後の一斉復帰を 8 波と、70.25〜73.25 秒切断後の一斉復帰を 1 波。毎波 4 読取・4 更新を異なる DB に発行する。全 8 DB で最終在庫、40 注文・100 明細、注文と明細の各合計 1,888,173 セントを検査する。各通番の集計値は試行の最終応答後に採取した。[試行別データ](trials.csv) · [各DBの通番](forks.csv) · [再現手順](recipe/REPRODUCE.md)
