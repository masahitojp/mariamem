# #233　prepared INSERT を Go の実行区間に分ける

**SUM の遅さを調べる次の対象は、生成 Go のトリガー実行中。** 固定版・P1 で、明細100件の Exec は元の SUM で17.578 ms、差分加算で12.589 ms。差4.989 msのうち4.626 ms（92.7%）を最外のトリガー区間で観測した。SQL 外の Go 経路は SUM 全体の3.552 ms（20.2%）を使うが、加算との差は平均0.070 msで、3組のうち1組では符号が逆だった。共通の待ちを含むこの経路を、SUM 固有の遅さの主因とする証拠はなかった。[各組](blocks.csv) · [全20区間と小計](stages.csv)

## 100明細の経過時間

単位は ms/100 INSERT。各組で計測ありの10 DB・1,000件を集計し、3組を等重みで平均した。各列の区間を足すと同じ列の Exec 時間になる。丸め前の各要求で ns 単位の一致を確認した。C は明細 INSERT トリガーだけを削除し、注文の監査を保持した対照。

| 排他的な実行区間 | A　元の SUM | B　差分加算 | C　明細トリガーなし | A−B |
|---|---:|---:|---:|---:|
| クライアントの Exec 開始 → ホストの要求書き込み開始 | 0.742 | 0.738 | 0.700 | +0.004 |
| 要求書き込み開始 → ゲスト受信・worker 起床 → SQL 開始 | 0.758 | 0.733 | 0.693 | +0.025 |
| SQL 実行のうちトリガー呼び出しの外側 | 4.542 | 4.249 | 3.881 | +0.293 |
| SQL 内の最外トリガー呼び出し | 9.484 | 4.858 | 0.018 | +4.626 |
| SQL 終了 → 応答作成・送出 → ホストが本文受信完了 | 1.202 | 1.173 | 1.122 | +0.029 |
| ホストの JSON 復号 | 0.337 | 0.331 | 0.321 | +0.006 |
| 要求 ID の照合・通知 → 呼出元・監視 goroutine の再開 | 0.221 | 0.216 | 0.207 | +0.005 |
| 監視側で先読み goroutine の終了を待ち、期限を戻すまで | 0.112 | 0.110 | 0.106 | +0.002 |
| MySQL 応答パケットの生成 → クライアント Exec 復帰 | 0.180 | 0.180 | 0.168 | 0.000 |
| **Exec 全体** | **17.578** | **12.589** | **7.216** | **+4.989** |

トリガーの区間は生成 Go の `Table_triggers_list::process_triggers` に入ってから戻るまで。入れ子は外側だけを加算した。C でもディスパッチ関数に1明細あたり2回入り、0.018 ms/100件を使った。A/B は4回。ここには生成 Go で実行する SQL、メモリ処理、待ちが含まれ、SQL アルゴリズム自体と Go 変換の上乗せは未分離。[排他的な表](grouped.csv) · [呼び出し数とフレーム長](frame-sizes.csv)

## ホスト側でどこを待っているか

SUM の SQL 開始前は1.500 ms、終了後は2.051 ms。応答側の最も長い単一区間は、ゲストの stdout への最初の非空書き込み開始から、ホストの reader が4 B ヘッダーを読み終えるまでの **0.749 ms**。続く本文受信は0.065 msだった。ここには書き手・読み手のスケジューリングが含まれる。OS パイプ自体の処理時間と、goroutine が実行可能になってから走るまでの時間は切り分けていない。

本文受信後は JSON 復号に0.337 ms、復号完了から ID に対応するチャネル通知直前までに0.013 ms、通知直前から Process.Call の再開までに0.169 msを使った。JSON は同じ入力サイズの加算でも0.331 ms。実際の要求フレームはヘッダー込み97 B、JSON 応答本文は214〜217 Bで、3条件で同じ分布だった。[20区間の実測](stages.csv) · [固定版ホストのフレーム受信・通知](https://github.com/masahitojp/mariamem/blob/5a7ec57bba4c4021c0bc1d3f34f00eed892bf19c/internal/guest/guest.go#L238-L284)

## 再現性と制限

| 組 | A−B 全体 | うちトリガー | うち SQL のその他 | うち SQL の前後 |
|---|---:|---:|---:|---:|
| ABC | 4.628 | 4.519 | 0.202 | −0.093 |
| BCA | 4.959 | 4.564 | 0.308 | +0.087 |
| CAB | 5.381 | 4.796 | 0.369 | +0.216 |

3組とも差の89.1〜97.6%がトリガー内に現れた。計測ありと通常版の100 INSERT ループ時間の対応差は、SUM で −3.75% / +1.34% / +3.73%。全条件では −18.18%〜+3.73%で、最も振れた第2組の加算・通常版には40.60 ms の DB が1件あった。すべて残し、数値は補正していない。計測器と共有ホストの変動を分離できず、0.070 ms の条件間差や細かい区間をそのまま削減できる時間とは見積もれない。[計測器の対照](observer-cost.csv) · [全 DB・全要求](runs)

固定製品 5a7ec57b、Apple M1 / macOS 27.2.1、Go 1.27.4、GOMAXPROCS=8、同時実行1 DB。事前検査・ウォームアップ込み24プロセス・222 DB・22,200 INSERT のトリガー定義、注文合計、在庫、監査、FK/CHECK、Close を確認。タイムライン11,100件すべてで要求の照合・時間順序・区間の和を確認し、ウォームアップを除いた9,000件から表を作った。両バイナリとも同じ SQL を実行する。今回測ったのは経過時間で、前回の独立 CPU 標本には加えない。[検査記録](verification.txt) · [ソース照合](source.json) · [再現手順と各計測点](recipe/REPRODUCE.md)
