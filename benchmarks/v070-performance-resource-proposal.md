# 性能調査から考える次の作業と v0.7.0 の範囲案

2026-11-02。**相談用の提案。v0.7.0の確定scope、実装開始、Issueの版移動、採用・公開の承認ではない。**
[性能調査の見取り図](performance-investigation-map.md)の18項目を判断の根拠とする。
追加計測は行っていない。

## 提案する方向

**最初に、候補を同じ分母で評価する「4指標の共通判定票」を固定する。その後に候補の実装順を選ぶ。**
v0.7.0は代表的なテスト用途での資源費用を示し、利用者が並列数を選べる状態を整え、
確認済みの初期化の無駄について採用判断を終える版、という方向を提案する。

前案は #63 の正規guest候補作成を先頭に置いた。Humanから「候補を増やす前に比較の分母を
固定する」との指摘を受け、**判定基準の整理を実装より先に置く**案へ修正した。
#63は原因・試作・source案があるため実装準備の進んだ候補だが、#68より総合効果が大きいと
証明されたわけではない。17.7MiBのゼロ書込み削減とキュー遅延改善を直接比較しない。

共通化の最も強い懸念は、判定票を埋める計測基盤の開発が新たな無期限の前提になること。
まず既存値と不足を整理し、採取は選んだ候補に限定する。取得不能な欄を判定保留として終了できるようにする。

#63自体には、実時間・CPU改善が小さい一方、正規guest buildと再生成の費用がある懸念も残る。
前の試作はFork wall約40.71→38.73ms、CPU約53.61→52.03ms、4子保持RSS増分約312.20→308.86MiB。
この規模に見合う最小変更に限定し、allocator全体の設計変更や追加campaignが必要になれば止める。
大幅な速度向上やpgmemとの差の解消を約束する候補ではない。

## v0.7.xの入口：共通の比較分母と判定票（草案）

**4指標を一組として常に報告する案には賛成する。ただし、ms・CPU時間・MiB・件数を
重み未定の単一スコアへ足し合わせない。** 総合評価は一枚にまとめ、悪化や欠測も同時に見せる。
以下は規約・新しい採用gateの確定ではなく、判断のための具体案。

### 提示された値を既存証拠へ対応付ける

| 指標 | 既存の参考値 | 元の分母・制約 |
| --- | --- | --- |
| 48子バッチwall | 637.7 / 972.6 / 1258.3ms、3バッチの中央値972.6ms | read1、P8、待機通知試作のbaseline。scalar trace付き。3例であり、5バッチ以上の条件は未達 |
| Fork CPU / 経過時間 | 49.23 / 36.41ms | 別の資源試験。4子を順に作って保持し、各process内4子の中央値→5processの中央値 |
| 保持RSS増分 | 1子+76.78MiB、2子+154.64MiB、4子+311.09MiB | baselineとの差をprocess内で取り、5process間で中央値。311.09÷4≈77.77MiBは4子保持時の平均増分で、各子の限界費用や専有物理メモリではない |
| キュー待ちp95 / >100ms | 21.908833ms / **5/144子で閾値超過** | 各子の最大submit-entry→task-start待ちを1標本とした分布。全taskのp95でも、SQL時間のp95でもない。3バッチ内の144子であり144独立反復ではない |

根拠: [Fork/保持資源](https://github.com/masahitojp/mariamem/blob/34f9c7704e042fb36360bbd3b91603ed6611326c/benchmarks/fork-resources.md)、
[待機通知試作のsummary](https://github.com/masahitojp/mariamem/blob/0eaa5cae11590b3c500fc40f16906137e251daf4/benchmarks/forkcompare/results-wait-accounting/summary.json)。
これらは**既存参考値の一覧**であって、同じ測定系列から取得した一つの現行baselineではない。
同じproduct commitでも、harness、観測負荷、実行履歴、集計方法が違えば同一分母とはしない。

### 今後の共通判定票に固定する案

共通manifestで、baseline/candidateのsource・guest・binary hash、変更点、toolchain、host、
GOMAXPROCS、1,000行のschema/seed、SQL oracle、read/write/purge設定、root/Snapshotの扱い、
測定版harnessと観測modeを固定する。候補に必要な一つの変更以外を揃える。
read1→4を評価するときだけ、そのsetting変更を明示した候補差とする。

| 欄 | 共通の定義案 | 実行・集計単位 |
| --- | --- | --- |
| 利用者のバッチ時間 | 同じ48子のFork→接続/SELECT1→COUNT/SUM→UPDATE/SELECT→Close。全子開始前から全子cleanup完了まで。root準備・build/downloadは別枠 | 主比較P8。fresh-process A/Bを交互順に固定5ペア、warmupは別枠。variant別5バッチのp50・全5値・ペア差を示す。P4は別欄の確認条件で、主集計へ混ぜない |
| Fork CPUと経過時間 | Fork呼出しそのもののprocess CPU差とwall。並行する子のprocess CPUを各Forkへ二重配賦しない | 別の直列保持modeで4子を順に作る。各process内4子中央値→5process中央値を固定。先に保持した子の背景CPUを含み得ることを明記 |
| 保持RSS | 同processの子なしbaselineから、接続退役・500ms待機後の1/2/4子保持時RSSへの増分。GC条件は前後で同一 | 直列保持modeの5ペアで取得。1子の直接差分と4子合計を主に示し、4で割った参考平均も併記可。バッチpeak RSSや仮想予約量とは区別 |
| キュー分布 | 子ごとの最大submit-entry→task-start待ちのp95、>100msの子数/全子数。submit内のmutex待ちも含む操作上の定義 | 同じ48子/P8の診断mode、固定5ペア。全taskの分布と別欄。バッチ別とプール値を両方示し、各子を独立process反復としない。drop・未実行task・欠測を併記 |

**分母を共通化することは、4指標を無理に同じprocessで採ることではない。**
主バッチはキューtraceなし、直列保持はCPU/RSSのためのmode、キューは同じ観測フックを入れた
診断A/Bとする。全modeでproduct/candidate差とfixtureを共通化し、modeごとにhash・条件を残す。
診断付きwallを主バッチwallへ混ぜない。将来安全にmodeを共用できても、定義変更として記録する。

最初は1host・1fixtureで、各mode固定5ペアを案とする。実施するmodeと費用は開始前に確認し、
取得不能なら欠測・判定保留として終了する。全候補×両platformの再計測をこの入口の条件にしない。
5ペアは初期の有限計画であり、統計的確実性の保証ではない。小標本p95や稀な超過件数は
その観測範囲の記述とする。p50だけで極端な遅いバッチを隠さず、全値と件数も残す。
観測されなかった遅延を解消済みとはしない。欠測はN/A、未確定はINCONCLUSIVEとして表示する。

### 「改善した」の判断案

- 正しさ・分離・cleanupは性能で相殺しない。
- 4欄のうち少なくとも一つに、事前に定めた実用上の改善があり、他欄が事前に合意した悪化許容幅内なら、総合改善候補とする。
- CPU/RSS削減でwallが横ばいなら「資源費用を改善」と書く。ゼロ書込み量や通知回数だけの変化は機構の改善であり、利用者向け性能改善とは区別する。
- 指標間のトレードオフが出たら、それを見せて判断する。重み付きスコアで隠さない。欠測が結論に必要なら判定保留で終了できる。
- 改善の最小幅・悪化の許容幅は**未決定**。5回測ればよい、すべて1nsでも悪化したら不合格、後から有利な指標を選ぶ、のいずれも採用しない。
- #68の既存分布gateとINCONCLUSIVEの結論は変更しない。この案を過去のreceiptへ遡及適用しない。

この判定票で候補の効果は比較しやすくなるが、異なる指標が改善する候補を自動で一列に順位付けは
できない。利用者の優先指標、実装・保守費用、安全性、確度も採用判断に含める。
「共通分母がある」ことと「優先順位が一意に決まる」ことは別。

### 数値閾値を決める前に、どこまで判断できるか

Humanから「判断基準を決めるのは難しそう」との指摘。改善率の合否をHumanへ丸投げしない。
Codexが観測・不確実性・実装維持費を照合して推奨を出し、Humanは利用者への価値と
その費用を受け入れるか判断する。最初から全指標に一律5%などの線を引く必要はない。

**次の小作業に投資する判断と、製品へ採用する判断を分ける。** 前者は既存証拠から可能でも、
後者に必要な共通指標が揃うとは限らない。下表は次の作業の推奨例であり、共通4指標での
総合ランキング、統計的有意性の判定、過去の実験gateを変更した新しいPASSではない。

| 候補 | 既存の各A/B内で確認できる事実 | 現時点の推奨と理由 |
| --- | --- | --- |
| #56 保護拡張 | protectは102→12〜13回。Fork wall/CPUは5組中3組で増加し、改善は一貫しない | 見送り。利用者指標の改善が示されず、保護境界と失敗処理を複雑にする費用に見合わない |
| #63 整列 | wall/CPUは5組中4組改善。4子保持RSSは全組で約2.83〜3.64MiB減。重複ゼロ化の除去は確認済み | 共通基準を整えた後の次の有限検証候補。理由の分かる局所変更で複数指標の改善方向が揃う。正規guest・共通バッチ・キューの不足があり、採用推奨はまだできない |
| #64 fresh-zero | wallは全5組改善。CPUは2組改善/3組増加。4子RSS削減は約0.56〜1.03MiB | 単独採用は見送りを推奨。小さな時間改善の価値は残るが、fresh-memory契約を追加維持する費用に対しCPU/メモリの根拠が弱い |
| read1→4 | 初回のバッチ短縮が、観測付きの後続比較では一貫しない | 保留。新しい計測器付きの結果と初回値を混ぜて改善率を決めず、今の根拠で既定値を変えない |
| 待機通知修正 | 子ごとの最大キュー待ち中央値/p95は改善、p99は非悪化条件を満たさない | 既存gateの判定保留を維持。欠落修正が到達可能という証拠と、総合効果・最悪側の改善は別 |

参照: [#56の5ペア](https://github.com/masahitojp/mariamem/blob/1e1b46b0a2208ad66eea8752e1c2d54475a9cbdc/benchmarks/growthprototype/results/summary.json)、
[#63の5ペア](https://github.com/masahitojp/mariamem/blob/30239a34977c6eaaa2ca804fc28e2553e498af48/benchmarks/bufferalignment/results/summary.json)、
[#64の5ペア](https://github.com/masahitojp/mariamem/blob/1597b7c41b26a75609a7ec383f3082792dc9cf3e/benchmarks/freshzero/results/summary.json)。

5組中何組改善したかだけを自動採用の基準にはしない。効果の大きさ、悪化例、実際に減った仕事、
正しさと保守費用を併せて評価する。異なる候補間で同じ分母になったという主張でもない。

既存のA/Bは変更そのものを含み、同一binaryのA/Aではない。baseline値の広がりにはhost状態や
経過時間の影響もある。その範囲を「測定誤差」として控除したり、そこから自動的に5%などの
悪化許容幅を導いたりはしない。5組の観測から稀なtailの安全域を決めることもできない。

提案するHuman判断は、まず次の程度の粒度でよい。

- 少しの改善でも、狭い変更で既知の無駄を除け、他の費用を増やさない候補は検討する。
- 小さい改善のために、新しい所有権契約・メモリ共有方式・大きな保守負担までは追加しない。
- 指標の改善が食い違う、必要な証拠が欠ける場合は保留として終了できる。採用まで追加測定し続けない。

これは価値と費用の方針案であり、「他の費用を増やさないことが証明済み」とするものではない。
正規候補の採用前には、共通4指標で何が改善し、何が変わらず、どの悪化を受け入れる必要があるかを
Codexが具体的な単位で提示する。未決定の数値幅は勝手に埋めず、判断不能ならその結論を返す。
この例示の追加によって新しいruntime比較やcandidate buildを開始する承認とは扱わない。

### いま行う統合と、その限界

| 既存候補 | 既存証拠で得られるもの | 共通判定票に対して不足/異なるもの |
| --- | --- | --- |
| #56 保護拡張 | 直列Fork CPU/wall、4子RSS、protect回数 | 48子主バッチとキュー分布 |
| #63 整列 | 直列Fork CPU/wall、4子RSS、ゼロ化量 | 48子主バッチとキュー分布。時間集計はprocess内平均で、上の案の中央値と違う |
| #64 fresh-zero | 直列Fork CPU/wall、保持RSS、構築/ready resident | 48子主バッチとキュー分布。時間集計方法も上の案と違う |
| read1→4 | 3ペアの48子バッチ、別cohortの1DB RSS、phase観測 | 5ペアに不足。共通直列Fork CPU/保持modeと、比較可能な候補前後キュー分布が揃っていない |
| 待機通知修正 | 診断付き3ペアの48子バッチとキュー分布 | traceなし主バッチ、共通直列Fork CPU/保持RSS、5ペアに不足 |

**定義・根拠・不足欄の統合は、新規計測なしでできる。候補を同条件で数値比較できる状態までは、
統合だけでは作れない。** 既存rawから集計を揃えられる場合も、harness差や観測負荷は消えない。
全5候補を一斉に再計測せず、共通判定票を合意した後、実際に選んだ候補で必要な不足だけ取得する。

この入口作業の終了条件は、4欄の定義、共通workload/mode、sourceの選び方、有限の反復計画、
既存値の帰属と不足欄、判断条件の未決事項を一枚で確認できること。
今回これらを草案として整理した。新しい計測器・CI・candidate buildや規約の強制実装は行っていない。
実行前には正確なbaseline source、toolchain/host、指標ごとの改善・悪化許容幅、実行予算を決める。
これが決まるまで #63 を含む新規比較campaignは開始しない。

## 既存の方針との関係

参照したmainのstatusは `c4742390cf4553636ceaa23c6732d48f76a37c9c`。
[既存のv0.7.x方針](https://github.com/masahitojp/mariamem/blob/c4742390cf4553636ceaa23c6732d48f76a37c9c/docs/project-status.md#v07x--guest-initialization-optimization-candidate-selection)
は、guest初期化の候補選定、大規模・100MiB用途、接続数や保持baseline/FDの詳細資源調整を
0.7系に置いている。**0.7.xの候補一覧をすべて0.7.0の完了条件にする判断はまだない。**
本案は0.7.0へ入れる最初の範囲を選ぶ提案であり、後続0.7.xの候補を削除しない。

config/host側を先に検討する既存方針も維持する。read1→4やhost保護拡張には既に限定試作の
結果があるため、guest変更より常に安いという理由だけでそれらを再試行しない。
共通判定票を置いた後の候補として#63を挙げるのは、狭いguest変更の根拠が相対的に強くなったため。

[Snapshot単位のFork上限 #53](https://github.com/masahitojp/mariamem/issues/53)は現在v0.6.1の項目。
これは利用者の資源調整手段として関連するが、0.7.0へ黙って移動せず、既存owner/進行と接続する。
Go fixtureの既存MaxForksと、直接Snapshot APIの上限設定も同一視しない。

#63は[3ファイルのsource案](https://github.com/masahitojp/mariamem/blob/2cb902610b1a5b423a71a59222e5ff793d81dfd8/docs/reviews/issue63-buffer-alignment-source-plan.md)
まで進んでいる。最初から設計調査をやり直さず、その残作業を使う。
pool専用のalignment指定、旧allocator入口の挙動、zero-filled/NULL-on-failureと既存freeを維持する。
共通allocatorの全callerを一律に2MiBへ変えない。

#63を選んで正規guest候補に進める場合の単位は、最小experimental.patch→guest build→Go再生成→host build→focused検証。
実行前にtoolchain・disk・source identityと予算を固定する。ビルド失敗の修正も同じ予算で数え、
新たなVM/allocator設計が必要なら別提案とする。採用時には必要な両platformの検証が残る。

## v0.7.0で狙う成果と、後続に置く候補

| v0.7.0の成果候補 | 完了の見方 |
| --- | --- |
| 代表用途の資源費用を利用者が判断できる | 小fixtureについて、Fork CPU/時間、保持0/1/2/4子のRSS、4/8並列バッチの費用を条件付きで説明。既存資料を再利用し、実装変更に必要な差分だけ再アンカーする |
| 利用者が並列数を明示的に選べる | #53の既存計画とGo fixture設定を整合させ、上限の対象・待機・キャンセル・失敗時の枠返却を説明。Snapshot上限をprocess横断メモリ制限とは説明しない |
| 確認済みの初期化の無駄について結論が出る | #63の最小正規候補について採用/見送りを決定。採用する場合だけ必要な候補検証を満たす。効果消失・未解決の安全性でも調査は終了できる |
| 資源の増大やcleanup失敗を隠さない | 既存の寿命・分離・Close/失敗検証を再利用。今回の変更で影響する経路だけ補う。新しい観測基盤の完成を製品完成の前提にしない |

これは「調査を完了したら自動的に0.7.0を出す」という条件ではない。
#63を見送る場合には、残る利用者向け成果で0.7.0のscopeが妥当かを見直す。
改善を出荷するために未知の最適化を際限なく追加しない。性能の採用条件とrelease判断は別に扱う。

後続0.7.xの候補として残すもの:

- 100MiBや準備の重いfixtureの専用調整。既存計測を活用し、0.7.0の全面matrixへ自動拡張しない。
- 多数baseline保持・FD圧、DB当たり16接続の詳細調整。需要・資源効果を確認してから個別に選ぶ。
- 子DBの約75MiB residentの用途別内訳、共有化/COW。似た内容のページが多いことだけで設計へ進まない。
- 自動メモリ予算、並列度の自動調整、プロセス横断制御。まず明示的な上限と説明を整える。
- Forkの残るCPU費用。既存profileはcycle全体なので、再開時はForkを対象にし、上位の変更可能な経路を一つ選ぶ。

48子バッチの旧harnessには、破損seedをきっかけとする8並列一斉キャンセルでcleanup timeoutの
観測もある。これは現候補での再確認済み不具合とは言えないが、資源制御の正しさに関わるため
忘れない。#53や今回の候補が同じ経路を扱う場合、既存failure検証で被覆できるか先に照合し、
必要なら有限の再現確認を行う。現候補でも実害が確認された場合は、性能改善より修正判断を優先する。
再現・安全性を確認せず「現在も壊れている」「既に修正済み」のどちらにも分類しない。

## 調査を広げ続けないための進め方

1. 各作業の冒頭に、見取り図の対象ID、利用者にとって変えたい指標、結果で決めることを一つ書く。
   例: F06の不要な再確保を除去でき、正しさと実際の費用に見合うため採用するか。
2. 最初に同条件の基準・変更点・主指標・許容するトレードオフ・有限の実行回数を決める。
   機構の成立、性能の有用性、正しさ、採用の判断を分け、後から有利な指標へ置き換えない。
3. 既存の[bounded investigation規約](https://github.com/masahitojp/mariamem/blob/c4742390cf4553636ceaa23c6732d48f76a37c9c/docs/development.md#bounded-investigations)
   を使う。初期既定はactive作業2時間（計測toolingは内30分）、heavy CI最大2回。
   失敗調査も同じ予算に含め、待ち時間は別記。新しい管理ツールやcontract lintは作らない。
4. 観測できない場合は、何が不足し、追加費用にどの判断価値があるかを示して終了する。
   新たな仮説は次の選択肢として残し、現作業の完了条件に足さない。
5. 候補が安定してから必要なplatform検証へ進む。探索の全段階で両OS・全fixtureを回さない。
   選んだ製品候補の既存正しさ・採用条件を弱めるという意味ではない。

今回決めたいことは、**4指標の共通判定票と比較分母を、v0.7.xの入口として固定するか**。
#63を先に実装する順序は改め、候補選択はこの判断の後に置く。
資源ガイドは既存証拠の整理から進められる。#68の再開や大規模メモリ共有の実装を同じ判断へ含めない。
