# 稼働中 50 ms・低頻度時 4 秒のスレッドプール保守間隔

**分離案を製品候補として検証することを推奨する。** 現行の 400 / 4000 ms、一律短縮の 50 / 500 ms、分離案の 50 / 4000 ms を固定リング候補上で比較した。分離案は P8 の 400 ms 以上の投入を現行の 5 件から 0 件に抑え、P1 のスイート経過を対応中央値で 23.64% 短縮した。8 DB の低頻度移行後は保守・CPU・割り込み起床が現行と近い値に戻り、低頻度からの最初の SQL は 16 件すべて接続込み 5 ms 未満で完了した。

採用判断に残るのは、切断から低頻度に移るまでの約 1 分間の負荷と、複数の DB が一斉に復帰する際の待ち。切断直後 30 秒の分離案の CPU は現行より毎秒 4.71 ms 高い（8 DB 合計、1 コアの約 0.47%）。今回の復帰試験は 1 台の Apple M1 で、各条件 2 試行、主キー 1 件の読取または更新を時間をずらして実行したもの。次の採用検証では再生成できる候補を用意し、同時復帰時の最初の要求と短い休止を繰り返す用途でこの判断が保たれるかを確認する。

現行で 400 ms を超えた 5 件は別々のスイートだった。同一ブロックで現行だけに遅延が出た組が 5、分離案だけに出た組が 0（正確 McNemar 検定、両側 p=0.0625）。今回単独で頻度の差を確定するには事象が少ない。前回、一律短縮で同じ方向の差（7/2,016 → 0/2,016）と保守処理によるワーカー補充待ちの短縮を確認した。現行に対する分離案の CPU は対応中央値 +0.28%（95% 区間 −0.14〜+0.69%）。[今回の P8 集計](p8-summary.csv) · [スイート対応結果](p8-tail-pairs.csv) · [前回の経路照合](https://github.com/masahitojp/mariamem/blob/2dedb9f95fd373d612166538187e47cdc5f860c4/benchmarks/p8-maintenance-period/results-20261121/README.md)

## 8 DB の常駐と復帰

すべての fork に同じデータを投入し、全接続を閉じて 120 秒間保持した。以下は 70–120 秒のプロセス全体の実測値で、各条件 2 試行の平均である。

| 設定（稼働中 / 低頻度） | CPU ms/秒 | 割り込み起床/秒 | 保守呼び出し/秒 | パッケージアイドル起床/秒 |
|---|---:|---:|---:|---:|
| 現行 400 / 4000 ms | 2.59 | 60.94 | 1.92 | 0.33 |
| 一律短縮 50 / 500 ms | 5.68 | 137.57 | 32.25 | 0.77 |
| 分離 50 / 4000 ms | 2.64 | 58.84 | 2.02 | 0.41 |

全試行で 70 秒までに低頻度への切替を 8 回ずつ記録した。分離案の後半の割り込み起床は 58.10、59.58 回/秒、現行は 60.20、61.68 回/秒。一律短縮の 2 巡目では後半に通常モードへの切替とワーカー開始が各 3 回あり、保守呼び出しが 48.60 回/秒に達した。OS の起床回数はプロセスに計上された回数で、消費電力換算はしていない。[各試行・各区間](idle-windows.csv)

切断直後の 0–30 秒は、分離案でも通常間隔が適用される。分離案の保守は毎秒 152.31 回で、一律短縮の 152.26 回、現行の 19.87 回と比べられる。同区間の CPU はそれぞれ 10.27、10.37、5.56 ms/秒。短い休止を繰り返す用途では、この区間の常駐コストが残る。[切替条件と固定ソース](https://github.com/MariaDB/server/blob/e4549ea60c98a8743ed4743d7f92174d8a0005d9/tpool/tpool_generic.cc#L550-L583)

| 設定 | 復帰直前に低頻度だった要求 | 接続込み読取の最大 | 接続込み更新の最大 | 400 ms以上 |
|---|---:|---:|---:|---:|
| 現行 | 16 / 16 | 4.03 ms | 4.57 ms | 0 / 16 |
| 一律短縮 | 15 / 16 | 4.13 ms | 4.73 ms | 0 / 16 |
| 分離 | 16 / 16 | 4.07 ms | 4.97 ms | 0 / 16 |

分離案は、それぞれの DB で直前の保守コールバックから 256–3,098 ms 経った時点で再接続した。各 DB の最初のアプリケーション SQL は主キー 1 件の在庫読取または在庫更新。接続確立後の SQL 単体は最大 1.50 / 2.07 ms だった。48 DB すべてで期待在庫、注文 40 件・明細 100 件、注文合計と明細合計 1,888,173 セントが一致した。この試験の復帰要求は 1 DB ずつで、同時復帰やプール枯渇時の遅延は未測定。[各要求の状態・タイマー位相・内訳](wakes.csv) · [集計](wake-summary.csv)
