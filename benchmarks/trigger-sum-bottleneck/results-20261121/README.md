# #233 SUM 再集計トリガーの局所費用

**判断は証拠不足。次に確かめる箇所は、SUM トリガーの注文 UPDATE が実行計画データを保存する際の割り当てに絞る。** `Update_plan::save_explain_data_intern → String_list::append_str → alloc_root → my_malloc → __wrap_malloc → dlmalloc` に至る経路で、同じ 32-bit ストア命令に SUM の trigger 配下標本の **70.8%、69.4%、66.2%** が集中した。加算・対照のこの経路では同命令への標本は各組 0 件だった。[命令別の 9 プロセス](allocator-site.csv) · [逆アセンブル](allocator-store.asm)

試作に進む根拠としては、3 組とも 15% 基準を超え、SUM で割り当て回数・サイズも増える点が強い。一方、各プロセスの対象 SQL は 52〜383 標本で、事前に定めた 3,000 標本・CPU 30 秒には全件未達。回数・サイズは要求単位で確認できたが、この呼び出し元が要求したバイト数や、当該ストアに CPU が集中する機序は未分離である。現時点では必要な計画情報を保ちつつ省ける処理と、その経過時間利益を特定できない。[判断規則と元の問い](https://github.com/masahitojp/mariamem/issues/233) · [T4 候補と限界](T4.md)

## 次に判断を変え得る証拠と費用

再計測する場合は、この計画保存経路からの割り当て回数・サイズと当該ストアの対象ページを同じ SQL 要求に結び付ける。初回書き込みの費用か、割り当てそのものの費用かは今回の PC だけでは区別できない。併せて十分な SQL CPU を採取すると、処理を試作対象にするかを判断できる。現行ハーネスで 3,000 SQL 標本に達するまでの概算は、各プロセス A 13 分前後、B 21〜28 分、C 76〜95 分。新しく同じ 9 プロセスを計測する場合は計約 **6.3 時間**、別に観測器の変更・ビルド時間が必要。各プロセスの今回の採取率を線形外挿した見積もりである。今回の計測は所定の予算で終了した。

## 計測条件と読み方

- 製品の `source_commit` は `5a7ec57bba4c4021c0bc1d3f34f00eed892bf19c`。#224 の保存証跡には関数表の現物がなかったため、固定 LLVM/WASIX 入力と Binaryen 133 から再生成した。リンク直後、最適化後の guest、展開後の関数表の SHA-256 が監査記録に一致。21,791 件から `emb_stmt_execute = Fn5581`、`process_triggers = Fn15566`、`dlmalloc = Fn152` を生成 Go の定義で確認した。[照合記録](phase1.json)
- macOS arm64、Apple M1、Go 1.27.4。P1 は同時に一つの DB に投入し、Go は GOMAXPROCS 8 / GOGC 100。各プロセスで共通のマスターデータと親 40 注文を準備し、スナップショットを取った。各 fork で同一の 100 明細を 1 トランザクションで INSERT して commit。元の UPDATE / DELETE 再集計、注文作成と status 更新の監査、索引・制約は共通。C は明細 INSERT トリガーだけを DROP する。[ハーネス](recipe/main.go)
- A/B/C の検査を先に各 1 回実行し、ABC / BCA / CAB を直列で実行した。全 fork で実登録本文を期待値と照合し、全 40 注文の合計・明細数、監査 40 件、全 500 商品の在庫、FK と CHECK のエラー番号、Close を確認した。各プロセスの先頭には実登録本文、各 DB には raw 時間と成功件数を残した。[CPU 記録](cpu/)
- CPU バイナリは無改変の製品コードを使う。親注文、検査、制約違反の照会はテキスト SQL で実行し、準備済みステートメントの実行は対象 INSERT に限った。raw 経過時間に含めるのは 100 回の実行とループの時間。pprof はプロセス全体で動かし、サンプルのスタックに対象 SQL 関数が現れたときだけ SQL に帰属させる。実験ハーネスのビルド情報に記録された外側の Git リビジョンと、ローカルモジュール置換で実際にビルドした製品コミットの両方を保存した。[入力とチェックアウト](build-inputs.json) · [バイナリ情報](cpu/environment.json)
- T1 は各 SQL 標本を一つの分類に割り当てる。標本 PC から SQL の方向へたどり、最初に該当した bounds、atomic、WASI、allocator、stack growth、memory growth を採用する。残りを sampled PC の関数・行から分類した。外側の trigger が見える標本を別集計し、再帰した trigger は一度だけ数えた。間接呼び出しの行には引数評価なども含まれ得る。生成 Go 本体内の変換コストと元の C/C++ の実行コストは未分離。[集計コード](recipe/reduce_cpu.py)
- T2 は同一スタック中の同一 Fn を一度だけ計上する累積 CPU。各組について A、B、対応差が上位の関数を載せた。T1・T2 とも各プロセスが完了した INSERT 数で正規化してから差を取る。異なる親子関数の累積値には同じ標本が含まれる。[T1](T1.csv) · [T2](T2.csv)
- T3 は別ビルドの overlay で 3 組を再生した。100 個のクライアント要求に SQL 入口・出口を 1 対 1 対応させ、module と trigger 深さで事象を帰属させた。allocator wrapper の成功バイト数は呼出し元の要求サイズ。dlmalloc はその下位の別観測点で、wrapper とは重複し得る。atomic のアドレス検査、個々の helper とインライン load/store も別々の観測点。SP 再解析は validate 関数内で固定 MariaDB の再解析が `parse_sql` に達した回数。WASI は実際の import 呼び出しごとに回数・経過時間を計測した。[観測点](bindings.json) · [T3](T3.csv)
- AtomicWait には値不一致による即時復帰も含む。実際に select へ入った区間、要求側の待ち区間の和集合、同一 DB の背景側で完了した待ちと SQL 区間との重複を別に集計した。背景側の重複だけで要求側の待ち原因は決められない。Go スタックのバイト数はプロセスの前後値で、個別要求の拡張回数は未分離。回数計測ビルドの経過時間と無観測ビルドの CPU を相互に換算しない。[要求別の原記録](events/)
