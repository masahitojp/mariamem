# 16 KiB 双方向ホストストリームの P8 検証

**書き込み主体の負荷では製品化候補として維持し、全負荷の既定方式への採用は保留することを推奨する。** P8 の100明細×8 DBで、SUM・加算・明細 INSERT トリガーなしは事前目安の6組中5組以上で短縮した。1 DB・8接続の読み書き混在でも中央値9.4%短縮した。一方、256 KiB超の応答では、経過時間は全組で短縮したもののプロセスCPUは全組で5.0〜9.0%増えた。独立DBを作成する負荷のピークRSSにも未説明の振れが残る。

同時実行中のキャンセル・切断・サーバー終了、応答を読み切った後の正常終了は、満杯を観測してから資源解放まで確認できた。直接の Process.Call の入力送信途中で Process.Shutdown を呼ぶ厳密な試験は6回とも EOF で失敗した。同じ部分送信の OS 対照でも6回中5回で EOF となった。呼び出しの排出を待たない内部停止経路の制限として証跡を残す。[故障試験・対照の集計](diagnostics.json) · [前回の P1 結果](https://github.com/masahitojp/mariamem/blob/de04aaa7aaf2b8d67c764012111feed6b3d34bac/benchmarks/host-framed-transport/results-20261121/README.md)

## P8 の性能

1波の経過は全8 worker が SQL を開始できる状態から、全員が処理を終えるまで。OS と候補は同じバイナリのモードで、6組で順番を交互にした。時間列は平均 ms/波、短縮率は対応する6組の中央値。CPU は全実行スレッドの合計。

| 負荷 | OS 経過 ms | 候補経過 ms | 経過の短縮率 | 短縮組 | CPU の変化 |
|---|---:|---:|---:|---:|---:|
| 8 DB・SUM 再集計 INSERT | 32.91 | 31.62 | 4.1% | 5/6 | 10.4% 減 |
| 8 DB・差分加算 INSERT | 23.29 | 21.52 | 6.4% | 5/6 | 17.4% 減 |
| 8 DB・明細 INSERT トリガーなし | 14.53 | 11.41 | 22.2% | 6/6 | 28.3% 減 |
| 1 DB・8接続、400 UPDATE＋400 SELECT | 26.60 | 23.78 | 9.4% | 5/6 | 9.9% 減 |
| 1 DB・8接続、256 KiB超の SELECT ×96 | 271.11 | 253.14 | 6.5% | 6/6 | **7.5% 増** |

大きな応答は接続・要求ごとのプレフィックスと256 KiBの本体を全件バイト照合した。1波のプロセスCPUは平均 1,444 → 1,551 ms、経過は約18 ms短縮。処理を早く終えられることと同時に、より多くのCPUを使っている。どのコピー・起床処理が増加分を生むかは今回の計測では未分離。混在は異なる行への更新と直後の読み戻しで、同一行でのロック競合は試していない。[対応値](pairs.csv) · [6組の範囲・CPU・確保量](summary.csv)

## メモリ

大きな応答での SQL 窓内の Go 確保量は平均 248.16 → 248.22 MiB/波、プロセス高水位RSSは 146.63 → 146.40 MiB。混在での確保量は 10.29 → 10.46 MiB/波。両方向の固定バッファの論理容量はインスタンスあたり32 KiB、8インスタンスで256 KiB。高水位RSSはGoのオブジェクトや固定バッファ以外のマッピングも含む。

8独立DBのうちトリガーなしの主比較では、プロセス高水位RSSが平均 **646.7 → 769.8 MiB**、6組中5組で増加した。対応差の中央値は **+189.2 MiB**。他の INSERT 条件でも組ごとの高水位の振れが大きかった。C 限定の追加6組では、全8 DBが同一段階で待機している時の現在RSSを別実行で取得した。

| C、追加実行の RSS（平均 MiB） | OS | 候補 |
|---|---:|---:|
| 8 DB準備完了後 | 537.5 | 536.6 |
| SQL 処理後・各DBの検証とClose前 | 538.8 | 537.9 |
| 全8 DBのClose・GC後 | 97.6 | 96.7 |
| プロセス高水位 | 542.9 | 541.4 |

追加実行では負荷終了ごとにGCし、同期点でRSSを読んだ。元のピーク増加はこの条件では再現しなかった。両者のリズムが異なり、同期点間の最大値を生む処理や長時間のメモリ傾向を確定できない。[初回のRSS](pairs.csv) · [追加6組のRSS](memory-pairs.csv) · [波ごとの追加記録](memory/)

## 満杯・停止・切断

実際のリンク済みゲストとホストを使い、診断用ビルドだけが読み手を止める。書き手が16 KiBを使い切り、未送信データが残った状態を確認してから各操作に進んだ。初回1回と同じ判定の追加5回。

| 満杯後の操作 | 要求側 | 応答側 |
|---|---:|---:|
| Process.Call の context をキャンセル、同じ原因を確認 | 6/6 成功 | 6/6 成功 |
| 実クライアントを切断し、ホストが切断を検知 | 6/6 成功 | 6/6 成功 |
| クライアントが問い合わせ中に Server.Close | 6/6 成功 | 6/6 成功 |
| 未完の直接 Call に Process.Shutdown を重ね、読み手再開後も完全な応答を要求 | **0/6、全件 EOF** | 6/6 成功 |
| 公開クライアント経路で再開・完全な応答を受信し、セッション終了後に Server.Close | 6/6 成功 | 6/6 成功 |

キャンセル・切断の試験はゲスト Done、転送ディレクトリ消失、サーバーの処分完了、残存セッション0まで確認。直接 Shutdown の追加対照は OS と候補を同じ16 KiB送信済み・残り未送信で止めた。残りの送信を再開すると、候補は6/6で EOF、OS は5/6で EOF、1/6で完全な応答。双方とも Shutdown は nil で終了し、資源は6/6で解放された。高水準の Server.Close はクライアントの受付を止め、worker を join してからゲストを停止する。内部 Shutdown は未完の Call すべての結果配送を待つ API としては使えない。[厳密な試験ログ](fault-repeats.txt) · [OS 対照](control-os.txt) · [候補対照](control-both.txt) · [クライアントの正常終了](public-drain.txt) · [固定版の終了実装](https://github.com/masahitojp/mariamem/blob/5a7ec57bba4c4021c0bc1d3f34f00eed892bf19c/internal/host/server.go#L380)

## 判断の条件

製品全体の既定方式に進むには、大きな応答でCPUが約7.5%増える交換条件を許容するか、実利用を代表するサイズ分布でCPU増加を抑えられることが必要になる。メモリ制約がある環境では、通常の GC と DB の生成・破棄を保ったままピーク時の常駐量を捕捉することが、RSS の判断を変え得る。現時点では経過時間の短縮だけで全用途への採用は勧めない。

主比較と事前検査は70プロセス・370波、2,960 worker、1,924 workload DB、243,904 件の対象 SQL 操作。メモリ追加試験は別の12プロセス。リング単体の競合検査は4ケース×10回で通過。実ホスト故障試験は通常のビルドで行った。macOS arm64・Go 1.27.4・GOMAXPROCS 8。MariaDB・ゲストには前回の固定版を使用。[環境](environment.json) · [検証分母](verification.json) · [ソース確認](source.json) · [競合検査](pipe-race.txt) · [再現手順](recipe/REPRODUCE.md) · [チェックサム](SHA256SUMS)
