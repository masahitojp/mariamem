# 計測前に固定した比較条件

仮説は、生成 Go の通常の memory32 load/store に限定して「定数の変位 + 幅」を生成時に畳み込むと、同じアクセス検査を保ったまま、P1 の SUM 明細 INSERT を短縮できること。調査対象は MariaDB 12.3.4 の同じ guest を変換した Go コード。一般の MemoryEA、atomic、bulk memory、WASI、MariaDB ソースを比較の両側で共通にする。

1. 同じコミット、Go ツールチェーン、CPU、ハーネスから、製品版と局所変換版の2バイナリを作る。一般の MemoryEA と新式を境界値と疑似乱数で差分検査する。動的な変位・幅、32 bit に収まらない定数の和、別のアドレス型があれば対象を黙って拡張せず、生成を停止する。
2. 事前実行は各バイナリで A/B/C 各1 DB。その後、P1・6組の比較。組内は ABC / BCA / CAB を2巡。各条件は独立2プロセス。奇数組は baseline → shim、偶数組は逆順。各プロセスは静的な入力で新しい DB を43回 fork し、各100明細を逐次投入。先頭3 DB は固定のウォームアップとして保存、後ろ40 DB が比較対象。外れ値を除かず、追加反復をしない。
3. 主指標はプロセス内40 DB の raw 100 INSERT 経過時間の中央値。副指標は同じ窓のプロセス CPU（user + system、背景スレッドを含む）中央値、DB の p95、実行ファイルの大きさ。組ごとに対応する差を求める。今回の局所案をさらに評価する目安は A の6組中5組以上で短縮、対応短縮率の中央値が2%以上、CPU の中央値も同方向であること。これはこの比較の判断用で、前回の SQL CPU 標本の不足は引き継ぐ。B/C・コードサイズ・ノイズも判断理由に残す。
4. すべての実行で元の SQL 検査を保持する。正しさまたはソース照合の失敗時は比較を停止。基準に達しなければ同じタスクで別の置換を試さず、この変換について判断を返す。ビルドは各バイナリ最大20分、比較は15分、作業領域8 GiB。
