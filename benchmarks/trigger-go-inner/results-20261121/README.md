# SUM 再集計トリガーは生成 Go のどこに時間を使うか

**100 明細を INSERT すると、SUM 再集計は差分加算よりトリガー内で 4.626 ms 多くかかる。そのうち 4.209 ms（91.0%）をサブクエリと JOIN の準備・最適化・実行に帰属できた。** 最大は `JOIN::optimize` 配下の 2.326 ms（差の 50.3%）。Go 側で次の候補を探すなら、この関数配下で繰り返される生成 Go の処理を優先する。CRC と同様に置換できる単一の演算を選ぶには、その下の時間内訳と入力・出力の等価性の証拠が必要になる。

## 二重計上を除いた経過時間

P1、40 注文・100 明細、各条件 4 組の平均。A は元の SUM、B は差分加算、C は明細 INSERT トリガーだけを外した対照。注文の監査トリガー等は全条件で有効。単位は ms/100 INSERT。対象の要求を実行した生成 Go の入口・出口で測った経過時間で、スケジューラ待ちも含む。

| 処理段階だけを計時した実行 | A SUM | B 加算 | C 対照 | A−B | 4組の A−B 範囲 |
|---|---:|---:|---:|---:|---:|
| サブクエリ・JOIN 配下 | 4.786 | 0.577 | 0.000 | 4.209 | 4.170〜4.258 |
| 上記を除く注文 UPDATE 配下 | 3.993 | 3.701 | 0.000 | 0.292 | 0.269〜0.306 |
| トリガー内の残り | 0.837 | 0.713 | 0.020 | 0.125 | 0.116〜0.129 |
| **トリガー合計** | **9.616** | **4.990** | **0.020** | **4.626** | **4.589〜4.656** |
| 参考・クライアント側の100 INSERT 全体 | 17.592 | 12.666 | 7.214 | 4.926 | 4.857〜5.012 |

分類は実行中の関数スタックに基づく。UPDATE の中でサブクエリを処理する時間は先頭行にだけ計上した。B の 0.577 ms は準備関数の共通グループ（JOIN::prepare を含む）で発生した。B のトリガー本文は差分加算で、JOIN 最適化、JOIN 実行、SUM 加算の観測回数はいずれもゼロ。C の 0.020 ms はトリガーの有無を調べる入口の時間を含む。[全区間](summary.csv) · [関数の対応表](recipe/sites.json)

| 主な観測点の排他的な時間 | A | B | A−B | トリガー差に対する割合 |
|---|---:|---:|---:|---:|
| JOIN 最適化 | 2.326 | 0 | 2.326 | 50.3% |
| JOIN 実行（SUM 加算の時間を除く） | 1.296 | 0 | 1.296 | 28.0% |
| サブクエリ・JOIN 準備 | 1.029 | 0.577 | 0.453 | 9.8% |
| SUM 加算関数 | 0.064 | 0 | 0.064 | 1.4% |
| UPDATE の実行計画保存 | 0.137 | 0.094 | 0.043 | 0.9% |
| ストレージエンジンの行更新 | 0.568 | 0.573 | −0.004 | −0.1% |

各行は、その観測点配下で、より深い別の計時対象に入っていない時間。JOIN 最適化は A の 100 INSERT で 101 回観測した。1 注文の第 1・2・3・4 明細を入れるとき、SUM の加算関数はそれぞれ 1・2・3・4 回、サブクエリ・JOIN 配下全体は平均 44.4・47.7・51.4・55.1 µs/INSERT。1〜4 明細の範囲では、1 明細目から準備と実行の費用がかかる。行数の多い注文への外挿は未検証。[組別の段階・回数](phases.csv) · [明細位置別](item-position.csv)

## メモリ確保・解放の内数

別の実行で、ゲストの arena 初期化・確保・解放、dlmalloc、dlfree の5関数を計時した。A は合計 1.140 ms、B は 0.609 ms、差は **0.531 ms**（4 組で 0.516〜0.547 ms）。同じ実行のトリガー差 5.199 ms に対して 10.2%。このメモリ差の 0.465 ms はサブクエリ・JOIN 内、0.028 ms はその外の UPDATE 内、0.039 ms はトリガーの残りで発生した。個別には arena 確保の差が 0.292 ms、dlmalloc が 0.103 ms、dlfree が 0.093 ms。各時間にはフックの負荷が含まれ、Go の GC や全メモリアクセスを計時した値ではない。[段階とメモリ関数の交差表](memory-cross.csv)

以前 CPU 標本が集中した UPDATE 計画保存では、A だけが 100 INSERT で 100 回、計 817,600 バイトを dlmalloc に要求した。4 組とも全 100 回が alloc_root 配下の補充だった。この dlmalloc の経過時間は 0.038〜0.044 ms/100 INSERT。局所的な割り当て増加は再現するが、計画保存全体の A−B も 0.043 ms で、今回の経過時間差への寄与は小さい。[段階別の計画保存・補充](phases.csv) · [先行のストア・ページ調査](https://github.com/masahitojp/mariamem/blob/4c3b928869a6ae9a09c52b894bd11d2b140a4c1e/benchmarks/trigger-sum-allocation/results-20261121/README.md)

## 対照と検証

外側だけの計時では A 9.509、B 4.868 ms/100 INSERT（前回は 9.484、4.858）。段階計時での A のトリガー時間は、対応する外側のみの計時に対し −0.5〜+3.1%。メモリ計時を加えると、A は段階計時より +9.6〜+12.7%、B は +8.1〜+14.2%。上の主表には段階計時を使い、メモリ比率の分母にはメモリ計時と同じ実行を使った。通常版の全体は平均で A 17.905、B 12.377、C 7.151 ms/100 INSERT。4組の範囲は観測したばらつきであり、最適化による短縮量は未測定。[4 モードの対応値](observer.csv) · [前回の要求全体の内訳](https://github.com/masahitojp/mariamem/blob/a81baaef944c69f67666277ae189422ef76d2c47/benchmarks/trigger-go-timeline/results-20261121/README.md)

固定製品 5a7ec57b、macOS arm64、GOMAXPROCS=8。MariaDB のソース・SQL の比較条件は前回を継承した。60 プロセス・588 DB・58,800 INSERT で注文合計、監査40件、在庫、制約と Close を検査。44,100 件のトレースを再読し、DB・要求 ID・順序を照合した。段階計時ありの各要求で全セルの和はトリガー全体に 1 ns 単位で一致した。事前検査とウォームアップを除く段階計時・メモリ計時の計 24,000 要求から内訳を集計。欠落、ID 重複、時間の不整合などを注入した5件の失敗例も検出した。[検証結果](verification.json) · [実行環境](runs/environment.json) · [再現手順](recipe/REPRODUCE.md) · [チェックサム](SHA256SUMS)
