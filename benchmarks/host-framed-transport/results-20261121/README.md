# ゲストとホストの間で prepared INSERT を往復させる費用

**両方向の内部 OS パイプを容量16 KiBのプロセス内バイトストリームに替える案を、製品化に向けた検証候補にすることを推奨する。** P1 の100明細で、対応する6組の短縮中央値は元の SUM で 1.498 ms（8.7%）、差分加算で 1.337 ms（11.0%）、明細 INSERT トリガーなしで 1.187 ms（16.7%）。両方向の変更は各条件で6組すべて短縮し、同一 OS 設定間の揺れを超えた。要求だけでも3条件に共通の小さな改善があった。

応答だけを替えると、応答ヘッダーは早く届くが、同じ設定で要求の送信側が遅くなり、全体の短縮は再現しなかった。輸送の方向を独立に足し算して予測するには、この相互作用が大きい。今回わかるのは P1 の特定の prepared INSERT に対する往復方式の効果で、並行接続や大きな応答における利益と、停止・キャンセルを含む製品上の適合性は別の判断になる。

## 要求ごとの時計を入れない比較

各列は同じ実行ファイル・SQL・入力の100 INSERT。通常版と両方向変更版は6組の平均 ms、短縮は各組で前後の OS 平均と対応づけた差・率の中央値。平均値の差と中央値にはずれがある。

| SQL 条件 | 通常の両方向 OS | 両方向変更 | 両方向変更の短縮中央値 | 要求だけの短縮中央値 | 応答だけの短縮中央値 | OS 同士の揺れの中央値 |
|---|---:|---:|---:|---:|---:|---:|
| 元の SUM | 17.200 | 15.670 | 1.498（8.7%） | 0.561（3.3%） | −0.118（−0.7%） | 0.246 |
| 差分加算 | 12.238 | 10.895 | 1.337（11.0%） | 0.393（3.2%） | 0.026（0.2%） | 0.096 |
| 明細トリガーなし | 7.043 | 5.843 | 1.187（16.7%） | 0.293（4.1%） | −0.172（−2.5%） | 0.046 |

事前の判定条件は、各 SQL で6組中5組以上が短縮し、短縮の中央値が OS 同士の絶対差の中央値を超えること。両方向・要求だけは3条件とも通過。応答だけの短縮は順に2/6、4/6、2/6組。両方向変更のプロセス CPU 短縮中央値も順に 1.813・1.610・1.478 ms/100 INSERT で、各6組とも減少。両方向の wall 効果から各方向単独の効果の和を引いた差は、組ごとの中央値で +0.977・+0.833・+1.175 ms。[全対応値](raw-pairs.csv) · [CPU と経過時間の集計](raw-summary.csv) · [方向の組み合わせ](interaction.csv)

## 要求別に見た変化

別バイナリの3組で、フレームと要求 ID を照合しながら計測した。短縮は対応する OS 設定との平均差。単位は ms/100 INSERT。

| 両方向を替えたときの区間 | 元の SUM | 差分加算 | 明細トリガーなし |
|---|---:|---:|---:|
| SQL 開始前の短縮 | 0.522 | 0.380 | 0.393 |
| SQL 終了後の短縮 | 0.710 | 0.601 | 0.635 |
| **SQL の前後の短縮合計** | **1.231** | **0.980** | **1.028** |
| うち要求書き込み開始 → ゲストの要求受信 | 0.294 | 0.244 | 0.253 |
| うち応答書き込み開始 → ホストのヘッダー受信 | 0.477 | 0.424 | 0.429 |

SUM で要求転送は 0.352 → 0.058 ms、応答ヘッダーまでは 0.761 → 0.284 ms、JSON 復号は 0.351 → 0.322 ms。応答だけを替えた場合もヘッダー受信までが 0.466 ms 短くなるが、要求転送が逆に 0.518 ms 延びた。B・C にも同じ向きの変化がある。これは Go の起床順、待ち、読み書き、カーネル処理を含む端点間の経過で、それぞれに要した CPU は未分離。輸送を替えると SQL 区間の壁時計にも変化があり（両方向で 0.746・0.304・0.256 ms 短縮）、SQL 外の実測だけで総差を説明しきれない。SQL やゲスト計算そのものの高速化はこの比較からは推定できない。主比較の raw と要求別 trace は別実行として集計した。[全区間](stages.csv) · [組別データ](stages-by-block.csv)

## 比較の境界と確認

- 固定製品 5a7ec57b、Mac M1・macOS arm64・Go 1.27.4、GOMAXPROCS=8/GOGC=100。クライアント接続は通常の Database.DialContext、試した箇所は linked guest の標準入力と標準出力の2本。標準の OS パイプは同じ実験用バイナリの対照設定。SQL、ゲストの製品コード、フレーム形式、ホストの JSON デコーダ、要求 ID の配送を保った。フレームの大きさと slot は各条件の同じ明細位置で全方式一致した。要求は97 B、応答は214〜217 B。[固定コミット](source.json) · [環境](environment.json) · [ホスト切替のコード](recipe/overlay.py)
- リングはコピーして所有権を切り離し、容量が尽きれば書き手が待つ。書き手の Close 後は読み残しを排出して EOF、読み手の Close で書き手も復帰する。両方向で1インスタンスあたり計32 KiBの Go バッファ。空書き込み単独の効果、バッファ容量の選択、製品全体のメモリ増減は未測定。[実験用ストリーム](recipe/pipe.go.txt) · [競合検査付き単体試験](pipe-tests.txt)
- 通常の OS パイプに4 KiBの受信バッファを加えた以前の試行では P1 全体の改善は小さく、無バッファ io.Pipe を応答だけに使った別の試行でも全体効果は不確かだった。バージョンと workload が異なるため、各方式の優劣を過去の数値との引き算で評価していない。[4 KiB 受信試行](https://github.com/masahitojp/mariamem/blob/abfffabff59c2015cd48273839477abbd9fb2d94/benchmarks/response-buffer/results-20261114/README.md) · [無バッファ応答の試行](https://github.com/masahitojp/mariamem/blob/10665616ba6f00d72b5563158a50bfb7cb2305d2/benchmarks/read-transport/README.md)
- 150プロセス、1,536 DB、153,600 INSERT で注文別合計・明細・在庫・監査・FK/CHECK・Close を検証した。定常区間は raw 90,000件、trace 36,000件。事前検査とウォームアップも保持。race 付きのストリーム単体試験を5回実行した。次の採用判断に必要なのは、並行利用（P8）・読み書き混在・大きな応答での全体時間とメモリ、バッファ満杯時のキャンセル・切断・正常停止の実行経路上の検証。今回の調査は P1 証跡の保存まで。[検証記録](verification.json) · [全プロセス・要求の原記録](runs/) · [再現手順](recipe/REPRODUCE.md) · [チェックサム](SHA256SUMS)
